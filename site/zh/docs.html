应用概况

DataZen 是一款跨平台桌面数据库管理工具，面向开发者与数据分析场景，在统一界面中连接多种数据库，并集成 AI 辅助与可编排的 Workflow 自动化。

它能帮你做什么

  • 管理多数据源连接（PostgreSQL、MySQL、MariaDB、SQLite、Redis 及插件驱动等）
  • 浏览 Schema、编写并执行 SQL、查看结果与图表
  • 用自然语言生成 SQL、诊断错误、分析执行计划
  • 通过上下文文件把业务规则、表说明等注入 AI
  • 用 Workflow 把「查询 + AI + 条件/循环」串成可复用流程
  • 用数据看板多图盯盘：后台定时刷新、阈值告警、历史回看与托盘常驻
  • 数据同步、备份恢复、配置导入导出、MCP 对接外部 AI 客户端
  • 用 Schema Diff 以源库为目标态对比结构，生成并受控部署 DDL

典型使用路径

  1. 首页新建连接并打开连接窗口
  2. 在设置中配置 AI Provider（API Key、模型）
  3. 在查询编辑器或 AI 侧边栏使用 NL2SQL / 对话
  4. 需要时添加上下文文件，提升生成准确度
  5. 把重复分析沉淀为 Workflow，一键执行
  6. 把核心业务指标做成数据看板组件，开启监控与告警
  7. 环境对齐时用 Schema Diff：对比 → 计划 → 审阅 → 部署

功能特色

多数据库统一体验

连接表单、Schema 树、SQL 方言与备份能力由数据库元数据驱动，减少硬编码分支；插件可在构建时按需引入。

查询与可视化

  • 多语句执行、查询历史与收藏
  • 结果表与图表双视图（柱/线/饼/散点/面积），支持自然语言调整图表配置
  • EXPLAIN 可视化与 AI 解读
  • 表结构编辑器：新建/改表、列与索引同草稿、SQL 预览后保存；控件启用由驱动按版本自报能力（不支持项会禁用并提示）；执行按语句逐步应用，非单事务

AI 辅助

  • NL2SQL：自然语言生成 SQL，完成后写入编辑器
  • AI 对话：结合当前库 Schema 回答问题、改写 SQL
  • 错误诊断 / 执行计划分析
  • 上下文文件：把本地文档注入提示词
  • Workflow：YAML 编排查询与 AI 步骤

数据看板与监控

  • 独立窗口多图网格，组件绑定 SQL + 图表配置
  • 后台 MonitorEngine 定时刷新；监控连接与 UI 会话隔离
  • 桌面通知 / Webhook 阈值告警；运行历史落盘可回看
  • 可选系统托盘：关主窗仍可继续监控（详见「数据看板」专章）

运维与生态

  • 跨库数据同步、备份与恢复
  • Schema Diff Deploy：源=期望态 → DDL 计划 → 审阅部署（详见专章）
  • 可作为 MCP Server 被 Claude Desktop / Cursor 等调用（推荐 datazen --mcp）
  • 也可作为 MCP Client 连接外部工具

AI 功能使用

准备工作

  1. 打开 设置 → AI，选择 Provider（OpenAI / DeepSeek / 自定义 OpenAI 兼容等）
  2. 填写 API Key、模型，保存并验证
  3. （可选）在「AI 上下文目录」中指定存放参考文件的文件夹

NL2SQL（查询面板）

  1. 打开连接窗口，进入查询标签页
  2. 点击工具栏「AI 生成 SQL」展开输入条
  3. 用自然语言描述需求，例如：「按销售渠道统计购物车数量」
  4. 需要时用 @ 引用上下文文件（见下一节）
  5. 点击「生成 SQL」；生成完成后 SQL 会写入下方 SQL 编辑器
  6. 检查后点击「执行」

AI 对话侧边栏

  1. 连接窗口工具栏点击消息图标，打开右侧 AI 面板
  2. 在「对话」标签中提问；默认会附带当前库的 Schema 摘要
  3. 可用 @ 附加上下文文件；发送后会注入到本次用户消息中

其他 AI 能力

  • 错误诊断：查询失败时可让 AI 解释错误并建议修复 SQL
  • EXPLAIN 分析：对执行计划做瓶颈解读与优化建议
  • 自然语言筛选：在表数据视图中用自然语言生成过滤条件

若未配置 AI，相关面板会提示前往设置；配置后无需重启即可使用。

上下文文件

有什么用？

AI 默认只能看到当前连接的 Schema（表结构摘要），并不知道你们团队的业务约定、字段含义、禁止改的表、示例 SQL 等。 上下文文件就是放在本地目录里的说明文档，在提问时按需注入到提示词中，让模型生成更贴近业务的结果。

典型用途：

  • 表/字段中文说明、枚举含义
  • 常用查询模板、命名规范
  • 业务规则（例如软删除字段、租户隔离）
  • 临时粘贴的需求说明、接口文档片段

支持的文件类型与限制

  • 扩展名：txt、md、sql、json、yaml/yml、csv/tsv、xml、ddl、schema
  • 单文件大小上限约 512 KB
  • 不会读取隐藏文件；路径有防穿越校验

上下文目录在哪里？

  1. 打开 设置 → AI
  2. 找到「AI 上下文目录」
  3. 留空则使用应用数据目录下的默认文件夹 contexts
  4. 也可指定任意本地文件夹，并把参考文件放进去

如何添加文件

  1. 在上述目录中新建或复制文件（可用「打开目录」在访达/资源管理器中操作）
  2. 也可建子目录分类存放；选择目录时会递归读取其中允许的文件

如何注入（@ 提及）

在以下输入框中均可使用：

  • 查询面板的 NL2SQL 输入
  • 连接窗口 AI 对话输入
  • Workflow 窗口的「AI 创建工作流」输入
  1. 输入 @，会弹出文件选择器（可继续输入关键字过滤）
  2. 选择文件或目录后，输入框中出现 @文件名 芯片
  3. 可添加多个；芯片上的 × 可移除
  4. 点击生成 / 发送时，应用会读取这些文件内容，并以类似如下形式拼进提示词： 
[Context: relative/path.md]
（文件正文）

（你的自然语言问题或对话内容）

注意：

  • 注入的是发送那一刻读到的文件内容，改文件后需重新引用再发送
  • 芯片对应路径会在发送后清空（避免误重复注入），文件本身仍保留在目录中
  • 上下文文件与「Schema 注入」是两套机制：Schema 由连接自动提供，文件需你用 @ 显式选择

Workflow 工作流

Workflow 把 SQL 查询、AI 分析、条件分支和循环 编排成可复用的 YAML 自动化流程 —— 可从界面、AI 侧栏或 MCP 触发。

  • 步骤类型：query、command、ai、 condition、foreach、merge、 transform —— 每一步都可单独指定连接、数据库、超时与错误处理。
  • 编写方式：编辑器同时提供可视化表单与 YAML 视图；「AI 创建」可从自然语言描述生成草稿。
  • 落盘 YAML 使用 snake_case（如 timeout_secs、then_steps、 as_var）。前端 TypeScript 显示的 camelCase 只是序列化差异，手写 YAML 请勿使用。
完整语法参考：所有字段、步骤类型、表达式与示例见仓库指南 —— workflow-guide.zh-CN.md （English）。应用内 Workflow 编辑器的 YAML 工具栏也有入口。

创建、运行、调度的点击式操作说明见使用手册 → Workflows。

数据看板

本文档说明 DataZen 运营看板（Ops Dashboard） 的完整用法：多图布局、后台定时刷新、告警、历史回看、托盘与导入导出。
事实来源：src-tauri/src/dashboard/、src-tauri/src/monitor/、前端 src/windows/dashboard/。
看板只引用已保存连接的 configId（与 MCP 一致），不会在看板文件里保存数据库密码。

1. 概述

运营看板是面向运维 / 值班 / 业务盯盘的独立窗口：在同一页面放置多个图表组件，每个组件绑定一条 SQL 与图表配置，由后台 MonitorEngine 按刷新间隔自动执行，并可将指标阈值推送到桌面通知或 Webhook。

能力 说明
多图网格 12 列布局，每个组件可独立占位与缩放（磁贴）
定时监控 组件级 refreshSec（下限 30 秒），关闭看板窗口后调度仍可继续
连接隔离 监控使用专用连接键 monitor:{configId}，不占用查询窗口会话
告警 数值阈值 + 冷却时间；通道：桌面通知、Webhook（邮件配置预留，暂不发送）
历史 每次运行落盘；可按时间点回看快照重绘图表（不重跑 SQL）
托盘 可选系统托盘：打开看板、暂停/恢复监控、退出
导入导出 看板单文件（仅定义）；应用数据 ZIP 可含定义 + 运行历史

与查询结果「表/图」切换的区别

  • 连接窗口里的图表是单次查询结果的可视化，不参与后台调度。
  • 运营看板是可保存的监控面：多组件、定时刷新、告警与历史。两者数据管线（ChartConfig / Recharts）可复用，产品路径独立。

当前边界（请勿按未实现能力使用）

  • 不是 Tableau 级 BI：无跨图联动筛选、语义模型、地图等。
  • 无头模式（如 --monitor）与登录项常驻服务为后续规划。
  • SMTP 邮件告警仅预留设置项，不会真正发信。
  • 每个组件为单条 SQL；多语句时取第一个结果集（并受结果行数上限约束）。

2. 概念与数据模型

2.1 看板（Dashboard）

字段 含义
id / name 唯一标识与显示名称
layout 网格：默认 12 列，rowHeight 控制行高
widgets 组件列表
enabled 看板是否参与后台调度（关闭后该看板全部组件不调度）

2.2 组件（Widget）

字段 含义
title 磁贴标题
configId 已保存连接 ID（须先在主界面建好连接）
sql 查询语句，结果驱动图表
chartConfig 图表类型、轴、聚合等（与查询结果图表配置同构）
layout { x, y, w, h } 网格坐标与尺寸
refreshSec 刷新间隔（秒），最小 30
alert 可选告警规则
enabled 组件是否参与调度

2.3 告警规则（AlertRule）

字段 含义
metric column：取某列（配合 agg）；或聚合语义
agg last / max / min / avg / sum（按列聚合时使用）
op > / >= / < / <= / == / !=
threshold 比较阈值
cooldownSec 冷却秒数，默认约 300，避免刷屏
channels desktop / webhook / email（email 暂不发送）

仅当运行成功且算出指标后才可能触发告警；查询失败不会当作「恢复」（避免误报）。

2.4 运行记录（WidgetRun）

每次调度或手动刷新会产生一条 run：ok / error / timeout，附带列名、行数据（单次最多约 500 行）、是否触发告警等，用于磁贴展示与历史抽屉。

2.5 磁盘位置

{应用数据目录}/dashboards.json
{应用数据目录}/dashboard-runs/
  {dashboardId}/
    {widgetId}/
      {yyyy}/{mm}/{runId}.json
      index.jsonl

默认每组件保留约 200 条 / 30 天（可在设置 → 监控中调整）。连接凭据仍只存在加密 connections 存储中。

3. 快速入门

3.1 前置条件

  1. 至少有一个已保存的数据库连接（看板绑定的是 configId，临时未保存连接不可用）。
  2. SQL 方言与目标库匹配；监控连接独立创建，需保证网络/权限可用。
    3.（可选）需要桌面通知时，在系统偏好中允许 DataZen 通知。
    4.（可选）Webhook：准备可接收 POST JSON 的 URL；也可在设置中填默认 Webhook。

3.2 创建并打开看板

  1. 主窗口左侧操作区点击 运营看板（仪表盘图标）。
  2. 在对话框中输入名称 → 创建，或选择已有看板 → 打开。
  3. 新窗口即该看板的网格画布。

3.3 添加第一个组件

  1. 工具栏点击 添加组件（或空状态引导）。
  2. 在编辑抽屉中填写：
    • 标题
    • 连接（下拉选择已保存连接）
    • SQL（建议返回少量聚合行，适合图表）
    • 刷新间隔（≥ 30 秒）
    • 图表类型与轴字段（可先跑一次再根据列名调整）
  3. 保存后磁贴出现；可点 全部刷新 立即执行。
  4. 确认图表正常后，保持看板 enabled、组件 enabled，后台即按间隔调度。

3.4 最小 SQL 示例

适合演示的 PostgreSQL / 通用写法：

SELECT 'Alpha' AS category, 100 AS amount
UNION ALL SELECT 'Beta', 200
UNION ALL SELECT 'Gamma', 150

图表：类型柱状，xAxis = category，yAxes = [amount]。

单值趋势类：

SELECT NOW() AS ts, COUNT(*)::float AS qps
FROM pg_stat_activity
WHERE state = 'active'

（具体系统视图因数据库而异；请换成你们环境的指标 SQL。）

4. 看板窗口操作

4.1 工具栏

操作 作用
全部刷新 立即对当前看板各启用组件执行一次
暂停 / 恢复监控 全局暂停 MonitorEngine（影响所有看板调度，不仅当前窗口）
添加组件 打开组件编辑抽屉（新建）
导入 / 导出 看板单文件（见 §8）

暂停状态会持久化；从托盘也可切换。看板窗口关闭不等于停止监控。

4.2 磁贴（组件）

  • 展示最近一次成功 run 的图表；失败时显示错误信息。
  • 编辑：修改 SQL、连接、图表、告警、刷新间隔。
  • 历史：打开运行历史抽屉，选择过去某次 run 快照重绘。
  • 布局：在 12 列网格中调整位置与大小（以产品 UI 提供的拖拽/尺寸为准）。

4.3 全局暂停 vs 看板/组件 enabled

开关 范围
工具栏 / 托盘「暂停监控」 整个引擎停止 tick
看板 enabled = false 该看板不参与调度
组件 enabled = false 仅该组件不调度

排查「为什么不刷新」时按上表逐项检查。

5. 图表配置建议

  • 优先 聚合后的少量行（几行到几十行），避免把大明细表直接塞进看板。
  • 单次 run 行数有上限（约 500）；超限会被截断，图表可能失真。
  • 列名稳定：告警与轴绑定依赖列名，避免 SELECT * 导致列顺序/名称漂移。
  • 类型与轴：数值列作 Y 轴；分类/时间作 X 轴；与连接窗口图表面板同一套 ChartConfig 语义。
  • 刷新间隔：生产环境建议按指标重要程度分级（如 30s / 60s / 300s），并留意 设置 → 监控 → 最大并行监控查询数，避免打爆数据库。

6. 告警

6.1 配置步骤

  1. 编辑组件 → 配置告警（若 UI 未展开可保存基础配置后再编辑）。
  2. 选择指标列与聚合方式、比较运算符、阈值。
  3. 设置冷却时间（秒）。
  4. 勾选通道：
    • 桌面通知：本机系统通知
    • Webhook：向 URL POST JSON（未单独配置时可用设置中的默认 Webhook）
    • 邮件：结构预留，当前不会发送

6.2 触发与冷却

  • 仅在 run 成功且指标可计算时评估。
  • 触发后进入冷却，冷却期内相同规则不会反复轰炸。
  • 失败 / 超时写入历史，但不应用「误恢复」逻辑清除告警状态。

6.3 Webhook 注意

  • URL 需可被本机访问；注意内网与 HTTPS。
  • Payload 为应用定义的 JSON（含看板/组件/指标等信息）；对接方按字段解析即可。
  • 默认 Webhook 在 设置 → 监控；组件亦可按实现覆盖（以实际编辑抽屉为准）。

7. 后台监控、托盘与关闭行为

7.1 MonitorEngine

应用启动后引擎就绪：存在启用的看板组件时按 refreshSec 注册调度；使用信号量限制并行查询，并对同一 configId 串行，降低连接抖动。

查询默认超时约 60 秒（超时记为 timeout）。

7.2 系统托盘

在 设置 → 监控：

选项 说明
显示系统托盘图标 有活跃监控组件时显示托盘
关闭时最小化到托盘 仅主窗口关闭时：监控开启且托盘启用则隐藏到托盘而非退出
默认 Webhook URL 告警未单独指定时使用
最大并行监控查询数 全局并发上限
运行历史条数 / 天数 每组件保留策略
应用数据导出包含运行历史 关闭则 ZIP 跳过 dashboard-runs/

托盘菜单通常包括：打开看板列表/窗口、暂停或恢复监控、退出应用。

7.3 关闭窗口 ≠ 退出

  • 关闭看板窗口：调度继续（除非已全局暂停或看板/组件 disabled）。
  • 关闭主窗口：若开启「关闭到托盘」且托盘可用，应用可继续在后台监控。
  • 真正退出：托盘「退出」或未走托盘路径的退出。

8. 导入 / 导出与备份

8.1 看板单文件

  • 导出：当前看板定义 → .datazen-dashboard.json（不含运行历史、不含连接密码）。
  • 导入：读入定义；若 id 冲突会分配新 id；目标环境需已有对应 configId 的连接，否则组件无法执行，需先导入连接或改绑连接。

8.2 应用数据 ZIP

现有「备份 / 应用数据」导出默认包含：

  • dashboards.json
  • dashboard-runs/（可用设置关闭）

导入整包可恢复看板与历史；连接凭据随现有备份机制一并处理。

9. 与 Workflow / AI 的关系

能力 Workflow 运营看板
目的 编排查询 + AI + 分支/循环，偏一次性或按需任务 持续盯指标、告警、历史曲线
定义格式 YAML 文件 dashboards.json / 看板 JSON
调度 手动 / MCP / UI 运行 MonitorEngine 定时
AI 步骤内可调用 不内置 AI 步骤（可在 SQL/外部流水线配合）

可把 Workflow 的聚合结果落到库表，再由看板 SQL 读取——二者互补而非替代。

11. 推荐实践

  1. 一组件一指标：标题写清业务含义（如「支付失败率」），SQL 只返回该指标所需列。
  2. 间隔分级：核心告警 30–60s，次要看板 5–15 分钟。
  3. 告警先桌面、后 Webhook：本地验证阈值正确再对接值班群。
  4. 控制并行：共享同一库的组件增多时下调最大并行查询数。
  5. 定期导出定义：看板 JSON 纳入配置仓库（不含密钥）；整包备份用于灾难恢复。
  6. 历史用于复盘：故障时段用历史抽屉对比，而不是反复重跑加重数据库压力。

Schema Diff

把「源库结构 = 期望态」对比结果，变成可审阅的 DDL，并受控部署到目标库。
入口：菜单 Schema Diff，或主窗口相关快捷入口。

1. 概述

步骤 做什么
对比 选源连接、目标连接与表，查看列/索引差异
计划 生成部署 SQL（默认仅加法）
审阅 / 部署 确认事务与破坏性确认词后，在目标库执行

方向约定（与 DBX 一致）

侧 含义
源连接 期望的结构（desired）
目标连接 要改成期望态的库（apply site）

界面标签：

  • 目标缺失（将 ADD）：源有、目标没有 → 计划里一般是 ADD COLUMN
  • 目标多余（将 DROP）：目标有、源没有 → 需开启「允许破坏性变更」才会进计划
  • 变更列：类型 / 可空 / 主键标记不一致

2. 快速入门

  1. 打开 Schema Diff 窗口
  2. 选择 源、目标（不能是同一连接）
  3. 在「表名」框填写一张或多张表（每行一个，或逗号分隔）
  4. 点击 对比 查看差异摘要
  5. 点击 生成部署脚本
  6. 在计划列表中核对每条 SQL 与风险标记（additive / destructive / rewrite）
  7. 进入 审阅 / 部署，按需勾选事务与回滚完整性要求
  8. 若含破坏性或改写类语句，输入确认词 DEPLOY 后再点 部署到目标
  9. 查看部署状态：committed / rolled_back / mixed / failed

也可随时 复制 SQL 或 复制摘要，不必真正执行部署。

3. 安全默认值

  • 默认计划为 仅加法：ADD COLUMN、放宽可空、CREATE INDEX 等
  • 勾选 允许破坏性变更 后才会生成：DROP COLUMN / DROP INDEX、收窄类型、SET NOT NULL 等
  • 计划中只要出现 destructive 或 rewrite，部署前必须输入 DEPLOY
  • 可选 要求完整回滚脚本：任一条语句缺少 rollbackSql 时禁止部署

生产库建议：先复制 SQL 到变更窗口人工审阅，并做好备份。

4. 事务与原子性

方言 DDL 原子性 中途失败时的状态
PostgreSQL 支持事务 通常为 rolled_back（先前语句撤销）
SQLite 支持事务（ALTER 能力有限） 通常为 rolled_back
MySQL / MariaDB 语句级自动提交 部分成功时为 mixed（不会假装整批回滚）
其他 按自动提交处理 类似 mixed / failed

目标方言不支持事务型 DDL 时，界面会禁用「在事务中执行」。

5. 多表与索引

  • 一次可填多张表，计划会按表拼接列级与索引语句
  • 可取消勾选 包含索引 只生成列变更
  • DROP INDEX 等往往没有完整反向 CREATE，会进入「回滚不完整」列表

主键结构变更目前不会自动进计划，请手工处理并留意警告。

6. 跨方言

源与目标方言不同时，列类型会经 数据同步 IR（column_to_ir → ir_type_to_native）映射。

  • 映射成功：出现在目标方言的 ADD/MODIFY 语句中
  • 映射失败：写入计划 警告 并跳过该语句（不静默生成错误 SQL）

SQLite 侧仍以 ADD COLUMN / 索引为主；复杂 DROP/MODIFY 会提示不支持。

7. 配置 JSON

可用剪贴板 导出 / 导入 配置（不含密码，只含连接配置 ID 与选项）： 

{
  "version": 1,
  "sourceConfigId": "...",
  "targetConfigId": "...",
  "tables": ["users", "orders"],
  "allowDestructive": false,
  "includeIndexes": true,
  "requireRollback": false
}

导入后需再点对比 / 生成计划；连接须已存在于本机配置列表。

8. 与 Data Sync / Data Transfer 的关系

产品 做什么
Schema Diff（本文） 结构对齐与受控 DDL 部署，不灌行数据
Data Synchronization 仅当表结构完全一致且双方有相同 PK 时，比较并应用行差异。见 docs/features/data-sync-guide.zh-CN.md
Data Transfer 异构或结构不同时的单向搬运（字段映射 + 类型映射）。单向搬运（字段映射 + 类型映射）。见 docs/features/data-transfer-guide.zh-CN.md

结构不一致时不要用 Data Sync「只同步部分列」；应先 Schema Diff，或改用 Transfer。

跨库建表 DDL 属于 Transfer / 适配器 IR；Deploy 路径是已有表上的 ALTER，不要和 Sync 的 Change Set 混用。

9. 当前不做

  • 视图 / 函数 / 触发器 / 存储过程同步
  • 在线改表工具（pt-osc / gh-ost）
  • 按相似度猜测重命名
  • 部署前自动备份
  • 经 MCP 一键部署（后续可能以高风险工具封装）
