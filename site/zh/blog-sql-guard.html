设计 SQL Guard：数据库工作台的语句级安全门网

如何在不需要 SQL 解析器的前提下，防止代价高昂的误操作。

2026 年 9 月 · 约 7 分钟阅读

问题是什么

每个数据库工具都面临同样的噩梦：用户不小心在生产数据库上执行了 DROP TABLE，或者一条没有 WHERE 的 DELETE 删掉了几千行。多数工具只提供两个极端选项——完全放开，或将连接锁死为只读。日常工作中，两者都不理想。

我们构建了 SQL Guard 来填补这个空白：一个轻量的、语句级的安全门网，位于 SQL 编辑器和数据库驱动之间，在危险模式到达数据库之前拦截它们。

设计原则

SQL Guard 遵循三条约束：

  1. 零依赖。不需要 SQL 解析器、语法文件或 tree-sitter。检查完全基于文本上的状态机运行。
  2. 多方言。必须同时适用于 PostgreSQL、MySQL、MariaDB、SQLite 和 Redis，无需按方言配置。
  3. 无误报。安全门网如果误拦合法查询，用户就会关掉它。CTE 中的 SELECT、dollar-quoted PL/pgSQL 块、注释丰富的迁移脚本都不能触发误报。

工作原理

1. 归一化

  • 空字节拒绝。包含 \0 的 SQL 被直接拒绝——空字节可以拆分关键字，绕过分类（如 DROP\0TABLE）。
  • 全角映射。全角拉丁字符（U+FF01 – U+FF5E）被映射为 ASCII 等价字符，使 ＤＲＯＰ 变为 DROP。

2. 语句拆分

归一化后的 SQL 在分号处分割为独立语句，同时尊重引号字符串、块注释、dollar-quoted 字符串和括号子查询。这确保了 SELECT 后跟 DELETE 会被检查为两条独立语句。

3. 注释剥离

每条语句会被剥离注释（-- 行注释、/* */ 块注释、# MySQL 注释），不触碰引号字符串字面量。剥离后的版本被独立重新分类。

这捕获了经典攻击：/* DROP */ SELECT 1——外层语句读起来是 SELECT，但注释隐藏了写动词。剥离后，扫描器看到 DROP，在只读模式下拒绝。

4. 动词分类

  • 读动词：SELECT、SHOW、DESCRIBE、EXPLAIN、PRAGMA、WITH、VALUES 等
  • 写动词：INSERT、UPDATE、DELETE、DROP、ALTER、CREATE、TRUNCATE、GRANT、EXEC 等

无法识别的动词在任何块注释中未找到写动词时会被放行，以处理厂商特定扩展的边缘情况。

5. Safe Mode

  • TRUNCATE 和 DROP 始终被阻止。
  • UPDATE 和 DELETE 必须带有顶层 WHERE 子句。扫描器追踪括号深度，确保 WHERE 不在子查询内部。

在架构中的位置

SQL Guard 运行在 Rust 后端中，查询到达数据库驱动之前：

  1. 用户在编辑器中输入 SQL 并点击运行。
  2. check_sql() 以连接的 read_only 和 safe_mode 标志运行。
  3. 如果任何语句未通过检查，整个批次被拒绝，并附带清晰的错误信息。
  4. 如果所有语句通过，执行正常进行。

这意味着 AI 助手、MCP Server 和 Workflow 步骤生成的查询都经过同一个门网。

我们踩过的坑

  • Dollar-quoted 字符串（PostgreSQL）：$func$ DROP TABLE foo; $func$ 是字符串字面量，不是 DROP。
  • 嵌套括号：DELETE FROM t WHERE id IN (SELECT id FROM s) 的顶层 WHERE 必须存在，子查询中的 WHERE 不算。
  • ORM 注释：某些 ORM 在实际查询前发送 /* ApplicationName=... */——这些无害注释不能触发误报。

下一步

SQL Guard 有意保持简单。未来可能的扩展：

  • 按表写权限（允许更新暂存表但阻止生产表）
  • 模式匹配警告（如对没有 LIMIT 的 SELECT * 发出提醒）
  • 审计日志：记录被阻止的语句及原因

亲自试试

SQL Guard 默认启用。打开 DataZen，创建连接，在连接设置中开启 Safe Mode，然后尝试运行 DELETE FROM users——你会看到它立即被拒绝，并被要求添加 WHERE 子句。
