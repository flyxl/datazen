Designing SQL Guard: Statement-Level Safety for Database Workspaces

How DataZen prevents costly mistakes — without a SQL parser.

September 2026 · 7 min read

The problem

Every database tool faces the same nightmare: a user accidentally executes DROP TABLE on a production database, or a DELETE without a WHERE clause wipes thousands of rows. Most tools offer a binary choice — allow everything, or lock the connection to read-only. Neither is ideal for daily work.

We built SQL Guard to fill the gap: a lightweight, statement-level safety gate that sits between the SQL editor and the database driver, catching dangerous patterns before they reach the wire.

Design principles

SQL Guard follows three constraints:

  1. Zero dependencies. No SQL parser, no grammar files, no tree-sitter. The check runs entirely on raw text with a state machine.
  2. Multi-dialect. It must work for PostgreSQL, MySQL, MariaDB, SQLite, and Redis without per-dialect configuration.
  3. No false positives. A safety gate that blocks legitimate queries trains users to disable it. We had to make sure SELECT inside a CTE, a dollar-quoted PL/pgSQL block, or a comment-rich migration script never triggers a false alarm.

How it works

1. Normalization

Before classification, the input passes through two normalization passes:

  • Null-byte rejection. SQL containing \0 is rejected outright — null bytes can split keywords and bypass classification (e.g., DROP\0TABLE).
  • Fullwidth mapping. Fullwidth Latin characters (U+FF01 – U+FF5E) are mapped to their ASCII equivalents, so ＤＲＯＰ becomes DROP.

2. Statement splitting

The normalized SQL is split into individual statements at semicolons, respecting quoted strings, block comments, dollar-quoted strings, and parenthesized subqueries. This ensures a SELECT followed by a DELETE is checked as two separate statements.

3. Comment stripping

Each statement is then stripped of comments (-- line comments, /* */ block comments, # MySQL comments) without touching quoted string literals. The stripped version is re-classified independently.

This catches the classic attack: /* DROP */ SELECT 1 — the outer statement reads as SELECT, but the comment hides a write verb. After stripping, the scanner sees DROP and rejects it in read-only mode.

4. Verb classification

The first keyword of the (stripped) statement is matched against two lists:

  • Read verbs: SELECT, SHOW, DESCRIBE, EXPLAIN, PRAGMA, WITH, VALUES, etc.
  • Write verbs: INSERT, UPDATE, DELETE, DROP, ALTER, CREATE, TRUNCATE, GRANT, EXEC, etc.

A statement with an unrecognized verb is passed through if no write verb is found in any of its block comments. This handles edge cases like vendor-specific extensions.

5. Safe Mode

Safe Mode adds two extra rules on top of read-only enforcement:

  • TRUNCATE and DROP are always blocked.
  • UPDATE and DELETE must have a top-level WHERE clause. The scanner tracks parenthesis depth to ensure the WHERE isn't buried inside a subquery.

Where it sits in the architecture

SQL Guard runs inside the Rust backend, just before the query reaches the database driver. The flow is:

  1. User types SQL in the editor and hits Run.
  2. check_sql() runs with the connection's read_only and safe_mode flags.
  3. If any statement fails the check, the entire batch is rejected with a clear error message — including which verb caused the rejection.
  4. If all statements pass, execution proceeds normally through execute_driver_command.

This means SQL Guard also applies to queries generated by the AI assistant, the MCP server, and Workflow steps — every SQL path goes through the same gate.

Edge cases we learned the hard way

  • Dollar-quoted strings (PostgreSQL): $func$ DROP TABLE foo; $func$ is a string literal, not a DROP. The scanner preserves dollar-quoted content as-is.
  • Nested parentheses: DELETE FROM t WHERE id IN (SELECT id FROM s) must have the top-level WHERE, not a subquery WHERE. The depth counter handles this.
  • Signed-off comments: Some ORMs emit /* ApplicationName=... */ before the actual query. These are harmless block comments and must not trigger false positives.

What's next

SQL Guard is intentionally simple — a text scanner, not a parser. Future extensions may include:

  • Per-table write permissions (allow UPDATE on staging tables but block production).
  • Pattern-based warnings (e.g., alert on SELECT * in queries with no LIMIT).
  • An audit log that records which statements were blocked and why.

Try it yourself

SQL Guard is enabled by default. Open DataZen, create a connection, toggle Safe Mode in the connection settings, and try running DELETE FROM users — you'll see it rejected immediately with a request to add a WHERE clause.
