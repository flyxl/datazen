| v01x-query-cancel-BUG-001 | **S3：未知 capability 的 Rust cancel IPC fail-open。** `get_capabilities()` 返回 `None` 时，`cancel_query_impl` 跳过 false 检查并继续调用 `driver.cancel_query`；因此未知 capability 在后端仍可能被当作可请求取消，绕过前端 unknown 的禁用门控。正常 QueryPanel 路径不会触发，但旧/直连 IPC 调用仍可触发。 | 待验证(新发现) | 1. 注册未提供 capability metadata 的 legacy/test driver（`register_test_driver`）。<br>2. 确认 `get_capabilities(db_type)` 为 `None`。<br>3. 调用 `cancel_query_impl`/`cancel_query`；当前代码仍执行 `driver.cancel_query`。<br>4. 使用默认 MockDriver 会得到成功返回；设置 `cancel_error` 则可观察到 driver 错误，证明 stub 已被调用。 | 静态证据：`src-tauri/src/db/registry.rs:169-183` 明确将缺失 metadata 定义为 unknown；`src-tauri/src/commands/query.rs:159-177` 仅在 `Some(false)` 时拒绝。已有 `commands::query::tests::get_explain_and_cancel_query` 用 legacy MockDriver 且 cancel 返回 Ok；全量 Rust Host：1182 passed。建议后续决定 unknown 是否必须在 IPC 层拒绝或返回显式 Unknown。 |
| v01x-query-cancel-BUG-002 | **S3：MySQL cancel 作用域过宽。** 当前实现不是同数据库或单 query 取消，而是实例级扫描并取消所有可见的非 Sleep 活跃线程；可能中断其他数据库、其他客户端或同一 DataZen 连接的并发查询。 | 待验证(新发现) | 1. 在同一 MySQL 实例的 DB-A、DB-B 分别启动活动查询，并保留 DataZen 控制连接。<br>2. 从任一 DataZen QueryPanel 点击 Cancel。<br>3. 观察 `information_schema.processlist` 查询只排除 `CONNECTION_ID()`、Sleep 和 `info IS NULL`，没有 `db = DATABASE()` 或目标 thread id 过滤。<br>4. 代码随后对所有结果执行 `KILL QUERY`，DB-A/DB-B 的非目标查询均可能被终止。 | 静态证据：`packages/drivers/mysql/src/mysql.rs:1450-1476`；SQL 没有 database predicate，循环对每个 processlist id 执行 `KILL QUERY`。对照 PostgreSQL `packages/drivers/postgres/src/postgres.rs:1282-1294` 至少限定 `datname = current_database()`，但仍是同库全 active backend。原 progress 的“同一数据库内”表述已在本验证记录中更正。驱动专属验证应留在 MySQL crate，不添加 Host 测试。 |
