# BUG-012 T14 自动重复模式无真实采集入口；确认冲突候选后出现两条 active；Chat 代码块不建立纠正基线

- 关联任务：T14 Memory v1：纠正、模式、冲突、失效
- 被测提交：`c25e836af`（`feat: add memory corrections patterns and staleness`）
- 严重度：阻塞 T14 验收
- 状态：待修复

## 结论

T14 的纯函数、IPC、冲突标记和 UI 原型大多有实现，但有三个影响验收的功能缺口：

1. **重复模式没有真实自动采集入口**：`ai_memory_extract_candidates` 只有 IPC 注册和测试调用，没有前端/查询执行链调用，也没有 query history 供给。真实应用里永远不会因为“14 天内同一 JOIN/过滤/表达式出现 ≥3 次”生成 pattern 候选；当前只有测试直接传历史数组才能证明纯函数可用。这直接阻塞 T14 的“重复模式生成候选”验收。
2. **确认冲突候选后同一槽位出现两条 active**：active + candidate 冲突可以正确保留两行，但 `ai_memory_confirm` 只是把 candidate 改成 active，没有归档旧 active 或应用 `resolve_memory_conflict` 的 Prefer/Merge 裁决。独立探针确认确认后 active 数量为 2，违反 PRD“同一 scope+kind+subject 只允许一条 active，新记忆确认时旧记忆 archived”。
3. **Chat 代码块的 AI SQL 不进入纠正学习**：`QueryPanel.runChatSql` 只 `updateSql` 并执行，没有像 NL2SQL 的 `applyAiSql` 那样写入 `aiGeneratedSqlRef` 基线。用户在 Chat 代码块 SQL 上修改并成功执行，不会提交 correction 候选。

## 证据

### 1. 重复模式无自动入口

全仓检索：

```text
rg -n 'memoryExtractCandidates|ai_memory_extract_candidates' \
  packages/frontend/src crates/datazen-desktop/src \
  --glob '!**/__tests__/**' --glob '!**/memory_tests.rs'
```

只命中：

- `crates/datazen-desktop/src/bootstrap/run.rs:436` IPC 注册
- `crates/datazen-desktop/src/commands/ai/memory.rs:939` 命令实现
- `packages/frontend/src/commands/ai.ts:129` 前端 invoke 包装

没有任何生产调用者；`AiMemoryExtractionInput.history` 只能由调用方临时提供。QueryPanel 执行完成只调用 `submitMemoryCorrectionIfNeeded` 和 `markStaleForSchemaDrops`，不调用抽取。测试 `extraction_creates_repeated_pattern_candidate_with_strict_json_fallback` 通过，但它直接构造 2 条 `AiMemorySqlSample` 并直调 IPC，不能证明真实 14 天窗口采集闭环。

### 2. 确认冲突候选后两条 active

独立临时 Rust 探针（已还原，不在提交中）：

1. 开启记忆；
2. 创建 active `Report locale / Use en-US`；
3. 创建同 scope+kind+subject 的 correction candidate `Use en-GB`，断言 `conflict == true`；
4. 调用 `ai_memory_confirm(candidate.id)`；
5. 统计 active 行。

实际结果：

```text
assertion `left == right` failed: PRD requires exactly one active row per slot
  left: 2
 right: 1
```

`ai_memory_confirm` 最终只是 `set_status(..., MemoryStatus::Active, "confirm")`，没有检查同槽位 active，也没有调用 T11 的 `resolve_memory_conflict` 做归档/合并。候选自己的 `structuredJson.conflict`/`conflictWith`/`conflictResolution` 有值，但确认动作没有消费裁决建议。

### 3. Chat 代码块没有纠正基线

`QueryPanel.tsx:524-533`：

```ts
const runChatSql = useCallback(
  (sql: string) => {
    updateSql(panelId, sql);
    void executionGate.requestExecute('selection', sql, { confirmWrites: true });
  },
  [panelId, updateSql, executionGate.requestExecute],
);
```

这里没有 `aiGeneratedSqlRef.current.set(...)`；只有 NL2SQL 的 `applyAiSql` 在 `:136-143` 写入基线。执行完成回调 `:494-518` 只从该 Map 取 original SQL，因此 Chat 代码块 SQL 的修改/成功执行不会走 correction 候选。T14 要求的是真实前端“执行成功 + SQL 被修改”入口，Chat 是现有真实 AI SQL 入口之一，当前只覆盖 NL2SQL。

## 非阻塞观察

- **schema diff/tree 未接**：目前只有 QueryPanel 成功执行 DDL 后触发 stale；schema diff/tree 的“树中删除/外部结构变化”没有调用 `markStaleForSchemaDrops`。若 T14 验收限定为真实执行 DDL，则当前路径可接受；若要覆盖所有 schema 删除来源，需要后续接线。
- **token 成本是固定估算**：`MEMORY_EXTRACTION_TOKEN_ESTIMATE = 320`，UI 文案是“预计每次约 {tokens} token”；它不是实际 provider 计量。PRD 的“开启时说明 token 成本”可被该估算满足，但若验收要求实际 token 消耗，则不满足。
- **`autoLearn` 关闭时** correction/extract 都返回空，符合可关闭要求。

## 建议修复方向（tester 未改代码）

- 将 `ai_memory_extract_candidates` 接到真实查询成功后的 history 供给（复用 query history / panel store），并在 `enabled && autoLearn` 下按窗口/阈值自动调用；否则 T14 的 pattern 验收没有落地入口。
- `ai_memory_confirm` 在确认 candidate 前读取同槽位 active，按 `resolve_memory_conflict` 执行 Prefer/Merge/Archive（至少保证一条 active），并写审计。
- Chat SQL 执行前也写入 `aiGeneratedSqlRef` 基线（或在 `runChatSql` 调 `applyAiSql`），使 Chat 修改后成功执行也进入 correction 学习。
