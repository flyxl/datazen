## 初始缺陷

1. 重复模式没有真实自动采集入口：`ai_memory_extract_candidates` 只有 IPC 和测试调用，没有查询执行链调用，也没有 query history 供给。
2. active + candidate 冲突保留后，`ai_memory_confirm` 只是把 candidate 改成 active，旧 active 未归档，确认后同槽位有两条 active。
3. Chat 代码块 `runChatSql` 没有写入 `aiGeneratedSqlRef` 基线，Chat SQL 修改后成功执行不会触发 correction。

### 1. pattern 自动采集

`QueryPanel` 成功执行回调现在在 `enabled && autoLearn` 时调用 `extractMemoryPatternsIfNeeded`。helper：

- 通过真实 `queryCommands.getQueryHistoryPage` 取 `limit=100`、`since=now-14d`、`order=recent` 的 history；
- 过滤 `success` 且非空 SQL；
- 以当前 SQL + history 调 `ai_memory_extract_candidates`，显式传 `windowDays=14`、`minOccurrences=3`；
- `autoLearn=false` 直接返回，不读 history、不调用 IPC；
- history/IPC 失败本地吞掉，不影响查询；
- 同一 connection/database 的并发用 in-flight 合并，并用 pending 保留下一次，测试覆盖突发第三次和执行重跑不丢失。

前端 4 个 helper 测试通过：关闭开关、成功 history 供给、失败吞掉、并发合并/重跑。QueryPanel paneRouting 测试也验证成功执行后真实调用 `getQueryHistoryPage` 和 `memoryExtractCandidates`。

### 2. 冲突确认

`ai_memory_confirm` 现在：

- 读取同 `scope_type+scope_id+kind+normalized subject` 的所有 active；
- 逐条用 T11 `resolve_memory_conflict` 生成裁决；
- 通过 `confirm_ai_memory_and_archive` 在同一 SQLite `Immediate` 事务中把旧 active 全部置为 archived 并写入 candidate active；
- 清理 `conflict`/`conflictWith`，写入 `conflictResolved`、`conflictResolution`、`archivedIds`；
- 写 `confirm` 审计和每条旧 active 的 `archive` 审计。

独立临时 Rust 探针（已还原）确认：确认后 active 数量为 1、旧 active 为 archived、`conflictWith` 已移除、`conflictResolved=true`、confirm/archive 审计均存在。全部通过。

### 3. Chat 纠正

`QueryPanel.runChatSql` 改为先 `applyAiSql(sql, paneId)`，再执行；`applyAiSql` 同时写 `aiGeneratedSqlRef` 和编辑器 SQL。因此：

- Chat SQL 原样执行不触发 correction；
- 用户修改 Chat SQL 并成功执行后，以原 Chat SQL 为 original、修改后 SQL 为 new 提交 correction；
- QueryPanel paneRouting 测试真实走 `requestQueryRun` → 编辑 → 成功执行，断言 correction 调用参数正确。
