# BUG-024 T24 数据修改 CTE 影响预览/Safe Mode 失效，函数式写 PRAGMA 被拒

- 关联任务：T24 写入提案与精确确认
- 被测提交：`b9272596c`（`fix: require write SQL and surface proposal row counts`）
- 复测时间：2026-11-07
- 严重度：阻塞 T24。影响预览误报写入；Safe Mode 可被数据修改 CTE 绕过。
- 状态：已验证（`4f1b49a3a`）

## 结论

BUG-023 的只读 SQL 拒绝和 rowCount 已修复。但新增的“必须是写语句”分类器允许
数据修改 CTE，而影响预览和 Safe Mode guard 仍只按顶层主语句判断，产生两个安全/
正确性问题；另外合法的函数式写 PRAGMA 被误拒。

## 复现 1：数据修改 CTE 的影响预览说不是写入

SQL：

```sql
WITH d AS (DELETE FROM users WHERE id = 1 RETURNING *) SELECT * FROM d
```

`propose` 成功，但返回：

```text
WriteImpact {
  statement_count: 1,
  tables: [],
  has_where: true,
  destructive: false,
  writes_data: false,
  schema_changes: false,
  summary: "1 statement(s): SELECT"
}
```

实际该 CTE 会删除 users 行，UI 却显示非写入 SELECT 影响，用户无法据此审查。
根因：`summarize_statements`/`build_impact` 只看 `sql_main_keyword` 和顶层
tokens，没有把 `has_data_modifying_cte` 的 DML 纳入 `writes_data`、目标表和摘要。

## 复现 2：Safe Mode 被数据修改 CTE 绕过

同一 SQL 先 propose（默认 config 可写），再以 `safe_mode=true` apply：

```text
store.apply(exact request, config, safe_mode=true, now)
=> Ok("WITH d AS (DELETE FROM users RETURNING *) SELECT * FROM d")
```

该 DELETE 没有 WHERE；若执行会绕过 Safe Mode 的 WHERE/DROP/TRUNCATE 约束。
宿主路径同样会进入 `execute_target`，因为 `is_write_only_sql` 已允许该写 CTE。
根因：`sql_guard::check_sql` 的 Safe Mode 分支只检查顶层主语句；CTE 顶层是
SELECT，所以 DELETE 的 Safe Mode 约束没有生效。apply 没有对嵌套 DML 再做
WHERE/DROP 检查。

## 复现 3：函数式写 PRAGMA 被误拒

SQLite 合法的 setter：

```sql
PRAGMA journal_mode(WAL);
```

`propose` 返回 `Err(NotWriteSql)`。写 PRAGMA 的另一形式
`PRAGMA journal_mode = WAL` 可以通过。`pragma_is_write` 只接受 `=`/包含 `=`
的 token，无法识别函数式 setter；用户验收要求“写 PRAGMA 仍可提案”。

## 修复建议

- 影响预览：识别 CTE 内的数据修改语句，填充 `writes_data`/目标表/摘要；或直接
  复用安全分级的 DML 检测结果。
- Safe Mode：在 `check_sql` 或 apply 层对数据修改 CTE 内的 UPDATE/DELETE/
  TRUNCATE/DROP 执行同样的 WHERE/禁止规则；补 CTE 绕过测试。
- PRAGMA：按已知可写 PRAGMA 支持 `name(value)` 形式，同时保持
  `PRAGMA table_info(...)` 等只读形式拒绝。

- 数据修改 CTE impact：`writes_data=true`、tables 含 users、summary 体现 DELETE；
  nested/multiple CTE 的 DML 均被收集且不会重复；无 WHERE DELETE 标记 destructive。
