# BUG-021 T22 Workflow 工具参数未转义：模型可改写只读 Workflow 的 SQL

- 关联任务：T22 插件/Workflow 工具桥
- 被测提交：`620133a10`（`fix: escape plugin SQL templates and redact previews`）
- 复测时间：2026-11-06
- 严重度：阻塞 T22。安全边界问题，不是测试环境问题。
- 状态：已修复（待独立复测）

## 结论

`620133a10` 已修复 BUG-020 的**插件** SQL 模板问题，但 Workflow 工具桥仍把
schema 校验后的模型参数直接作为 Workflow 变量交给 `WorkflowExecutor`。Workflow
引擎的 `WorkflowContext::resolve_template` 使用正则 `replace_all` 原样替换
`{{name}}`，没有 SQL 字面量转义，也没有在只读直跑或审批前做模板安全检查。

因此模型可以通过 Workflow 工具参数改写 Query 步骤的 SQL：只读 Workflow 无审批直跑，
非只读 Workflow 审批后同样执行被改写的 SQL。这违反 T22 Workflow 验收项
“模板参数转义”。

## 复现

最小只读 Workflow：

```text
id: wf-escape
variables:
  - name: name, type: string, required
steps:
  - type: query
    id: q1
    sql: "SELECT * FROM users WHERE name = '{{name}}'"
```

通过 `workflow_wf-escape` 调用，参数：

```json
{"name":"O'Brien"}
```

实际：

```text
authorize_bridge_tool_with_port(...) == Allow
port.request_count() == 0                 // 只读直跑，无审批
execute_workflow_tool(...) 成功
mock.query_log() == "SELECT * FROM users WHERE name = 'O'Brien'"
```

期望 `O''Brien` 或 fail closed；实际 `O'Brien` 直接闭合字符串。把参数换成
`x' OR '1'='1` 会改写 `WHERE` 条件，模型可读取 Workflow 作者未预期的行。

## 根因

- `crates/datazen-desktop/src/commands/ai/bridge.rs:640`：

  ```text
  WorkflowExecutor::execute(&workflow, state, None, &variables)
  ```

  只做 schema 校验，没有沿用 BUG-020 的 SQL 感知渲染/预校验。

- `crates/datazen/src/workflow/application/context.rs:71-79`：
  `resolve_template` 用 `regex::replace_all` 把 `{{...}}` 直接替换为变量值。
- `crates/datazen/src/workflow/engine/executor.rs:498` 将结果直接作为 Query SQL 执行。

插件路径 `render_input_template_with_dialect` 的安全检查没有覆盖 Workflow 引擎。

## 影响

- 只读 Workflow 直跑时，模型参数可扩大/改变查询条件，绕过 Workflow 作者固定的
  WHERE 约束并读取未预期数据。
- 非只读 Workflow 在用户审批后执行被改写的 SQL；审批载荷也没有该 SQL 的转义预览。
- T22 “Workflow 只读直跑/非只读审批 + 模板参数转义”验收项仍不完整。

## 修复建议

在 Workflow bridge 边界对每个可达 Query/Command 步骤的 SQL 模板做与插件一致的
SQL 上下文渲染/预校验（含错误回退路径），并使用目标连接的 SQL 方言；字符串参数
按字面量转义，字符串外只允许 number/bool/NULL，不安全模板在 Allow/审批/执行前
fail closed。不能只校验变量 schema。

## 修复

本地提交信息：`fix: apply SQL-safe rendering to workflow templates`。

- 把 BUG-020 的 SQL 感知渲染器从 AI 模块下沉到 `datazen::sql_template`，插件与
  Workflow 共用同一个 lexer/resolver；没有复制第二套转义实现。
- Workflow 执行入口不再调用 `WorkflowContext::resolve_template(sql)`：
  Query 步骤的 `sql` 和 Command 输入中的 `sql`/`*_sql` 字段改走同一渲染器；
  非 SQL 字段（AI prompt、数据库/连接名、普通 input 字段）仍保持原有原样替换。
- `WorkflowContext` 保留输入变量的 JSON 类型，并新增 typed 表达式解析；`steps.*`
  （含 `rows[0]`/`rows[0].value` 形式）和 foreach 循环变量按实际类型渲染。字符串
  只在单引号内转义，字符串外只接受 number/bool/NULL。
- `WorkflowHost` 新增目标连接方言端口；桌面 AppState 按连接 driver 提供
  `sql_literal_dialect()`，MySQL/ClickHouse 使用反斜杠转义，标准 SQL 不转义。
- Workflow 只读分类之后、任何 Allow/审批/执行之前，遍历全部可达步骤（含 condition
  分支、foreach body、error fallback）预校验 SQL 模板；失败 audit deny，不弹审批、
  不执行。
- 非只读 Workflow 的审批 SQL 用脱敏后的变量/默认值渲染；`steps.*` 和循环值在审批
  时尚不存在，以 SQL NULL 代入，不泄漏凭据。多 SQL 步骤按执行顺序拼接预览。
- 新增共享 executor 黑盒与 desktop bridge 测试：`O'Brien`、注入串、数字/LIMIT、
  `steps.*`/loop 类型、MySQL 反斜杠、字符串外字符串、注释内 placeholder、审批 SQL
  无凭据、只读直跑与非只读审批。
