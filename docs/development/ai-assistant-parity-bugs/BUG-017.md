# BUG-017 T19 MCP scope 只校验工具参数，SQL 可跨库/跨 schema 执行；审计与 schema resource 仍有缺口

- 关联任务：T19 MCP scope、逐次审批、审计
- 首次被测提交：`57bb4f4bd`（`feat: scope and audit MCP tool calls`），父 `2f22727f4`
- 前次修复后复测：`f1a94b2d1`（`fix: enforce MCP SQL scope and complete audit`），父 `5e4cee9dc`
- 最新复测提交：`0006d30ca`（`fix: enforce SHOW scope and resolve default targets`），父 `5b6e2d169`
- 复测时间：2026-11-06
- 严重度：阻塞 T19 验收。scope 外 `query` 已在真实 MySQL/PostgreSQL 上成功返回数据，且审计把目标记成 scope 内的默认库。
- 状态：待修复（`0006d30ca` 复测仍失败：默认库为 null 的 `SELECT 1` 未通过）

## 结论

T19 的审批主路径（Allow once / Deny / timeout / cancel、无 UI 时 fail closed）、
显式 `database`/`schema` 参数校验、追加式审计和前端设置项基本可用；但 T19
“scope 外调用在任何执行前拒绝（query/metadata/schema resource）”不成立：

1. **database scope 不校验 `query` 的 SQL 目标。** 允许库设为 `mysql`、连接默认库
   `mysql` 时，`SELECT COUNT(*) FROM datazen_demo.test_orders` 成功返回 3 行；
   `SELECT COUNT(*) FROM information_schema.tables` 成功返回 351 行。`datazen_demo`
   和 `information_schema` 都在允许的 `mysql` 之外。
2. **namespace scope 不校验 `query` 的 SQL 目标。** 允许 namespace 为 `public` 时，
   `SELECT COUNT(*) FROM information_schema.tables` / `pg_catalog.pg_class` 仍成功
   返回 221/459 行；`query` 甚至没有被当作 namespace-targeted tool。
3. **schema resource 在设置 namespace scope 后全部不可用。** 允许库 `postgres`、
   允许 namespace `public` 时，`resources/read` 读取 `datazen://schema/conn_e2e_pg/postgres`
   仍被拒绝：`schema resources cannot verify a namespace`。这是把合法的 scope 内
   resource 误拒。
4. **连接默认库/schema 为 null 时误拒。** 现有真实连接 `conn_e2e_pg` /
   `conn_gimlk4k4` 的 `database`、`schema` 为 null。配置 database scope 后，
   `query` 报 `must specify a database inside the scope`；配置 namespace scope 后，
   `list_tables` 报 `must specify a schema inside the scope`，即使 PostgreSQL 的
   实际默认库是 `postgres`、默认 schema 是 `public`。`with_scope_defaults` 只复制
   `Some` 值，没有驱动默认回退。
5. **审计字段不完整/有错。** 无 scope 的 `query` 实际使用连接默认库 `postgres`，
   但审计的 `databaseName` 为 null；MySQL `SELECT` 实际返回 1 行，但审计
   `rowCount` 为 0（先读 `rowsAffected`，MySQL SELECT 为 0）；读调用和 scope 拒绝
   的审计行 `requestId` 均为 null，审计 UI 也没有 requestId 列。

Coder 文档已明确写下“跨 database 的 SQL 限定名无法仅凭 scope 静态证明”，但这条
边界与本次验收的硬要求冲突，不能作为通过理由。

## 独立复现

使用 `datazen_desktop --mcp`（headless stdio），`DATAZEN_DATA_DIR` 指向隔离数据
目录，token 由 `mcp.token` / `DATAZEN_MCP_TOKEN` 提供；协议为 JSON-RPC
`initialize` → `notifications/initialized` → `tools/call`。

### 1. MySQL：database scope 被 SQL 跨库执行绕过

设置：

- `mcpAllowedConnectionIds = ["conn_gimlk4k4"]`
- `mcpAllowedDatabases = ["mysql"]`
- 连接 `conn_gimlk4k4` 的 `database = "mysql"`

调用：

```json
{"name":"query","arguments":{"connection_id":"conn_gimlk4k4","sql":"SELECT COUNT(*) AS n FROM datazen_demo.test_orders"}}
```

结果：`isError=false`，`rows` 为 `[[3]]`。`datazen_demo` 不在允许的 `mysql` 内。
同一进程再执行 `SELECT COUNT(*) FROM information_schema.tables` 返回 351 行。
两次调用的审计均为：

```json
{"connectionId":"conn_gimlk4k4","databaseName":"mysql","tool":"query","decision":"allow","rowCount":0,"requestId":null}
```

审计既没有记录实际访问的 `datazen_demo`，又把 1 行结果记成 `rowCount: 0`。

### 2. PostgreSQL：namespace scope 被 SQL 跨 schema 执行绕过

设置：

- `mcpAllowedConnectionIds = ["conn_e2e_pg"]`
- `mcpAllowedDatabases = ["postgres"]`
- `mcpAllowedNamespaces = ["public"]`
- 连接 `conn_e2e_pg` 的 `database = "postgres"`、`schema = "public"`

调用：

```json
{"name":"query","arguments":{"connection_id":"conn_e2e_pg","sql":"SELECT COUNT(*) AS n FROM information_schema.tables"}}
{"name":"query","arguments":{"connection_id":"conn_e2e_pg","sql":"SELECT COUNT(*) AS n FROM pg_catalog.pg_class"}}
```

两次均 `isError=false`，分别返回 221、459 行。审计写的是
`databaseName=postgres, namespace=public`，与 SQL 实际访问的
`information_schema` / `pg_catalog` 不符。

### 3. schema resource 误拒

设置同上（允许 `postgres` + `public`），调用：

```json
{"method":"resources/read","params":{"uri":"datazen://schema/conn_e2e_pg/postgres"}}
```

结果：

```text
MCP namespace scope is restricted; schema resources cannot verify a namespace
```

`public` 明确在允许列表内，但 resource 路径没有 namespace 可校验，于是被全拒。

### 4. 默认库/schema 为 null 的误拒

- 连接 `conn_e2e_pg` 的 `database = null`，设置 database scope `["postgres"]` 后
  执行 `query` `SELECT 1`：报
  `MCP database scope is restricted; tool 'query' must specify a database inside the scope`。
- 连接 `conn_e2e_pg` 的 `schema = null`，设置 namespace scope `["public"]` 后执行
  `list_tables`（`database=postgres`）：报
  `MCP namespace scope is restricted; tool 'list_tables' must specify a schema inside the scope`。

同类连接的真实默认库/schema 分别由驱动提供（PostgreSQL 为 `postgres` / `public`），
不是 scope 外目标；这里应是可解析的默认目标，而不是误拒。

### 5. 审计缺字段/行数错误

无 scope 时执行：

```json
{"name":"query","arguments":{"connection_id":"conn_e2e_pg","sql":"SELECT 1 AS ok"}}
```

结果 `isError=false`，审计行为：

```json
{"databaseName":null,"namespace":null,"tool":"query","decision":"allow","rowCount":1,"requestId":null}
```

该调用实际使用连接默认 `postgres`，但 `databaseName` 为 null。scope 拒绝的审计行同样
`requestId` 为 null；前端表格只展示 when/who/connection(+database)/tool/decision/rows，
没有 requestId 与 namespace 列。

## 根因定位

- `crates/datazen/src/mcp/domain/policy.rs:75-98`：scope 只从工具参数
  `database` / `schema` / `namespace` 取值；`sql` 虽被读出，只用于权限/审批分类，
  没有数据库/schema 目标解析。
- `crates/datazen/src/mcp/domain/policy.rs:116-124`：`targets_namespace` 不含
  `query`，namespace scope 对 query 完全不生效。
- `crates/datazen-desktop/src/mcp/server.rs:243-265`：`with_scope_defaults` 只填
  连接配置中的 `Some` 默认值；连接为 null 时不回退驱动默认，也不提示配置。
- `crates/datazen/src/mcp/domain/policy.rs:160-183`：namespace scope 非空时，
  `ensure_schema_resource_scope` 无条件拒绝 schema resource。
- `crates/datazen-desktop/src/mcp/server.rs:385-420`：审计目标取自
  `prepared.plan` / 原始参数，默认库未回填时为空；`find_row_count` 先读
  `rowsAffected`，导致 MySQL SELECT 的 1 行被记成 0。
- `packages/frontend/src/windows/settings/McpSettingsSection.tsx:538-563`：审计表
  未展示 requestId/namespace。

## 修复方向（仅记录，本次测试未修改生产代码）

- 在 database/namespace scope 激活时，对 `query` 的可静态证明目标做校验；
  无法证明的跨库/跨 schema SQL（包括动态 SQL）应拒绝或通过受控 session
  默认库/search_path 约束，不能以连接默认库代替 SQL 目标。
- schema resource 需要带 namespace 的寻址方式，或在允许 namespace 时按可验证的
  resource 结构放行；不能对所有 namespace scope 一律拒绝。
- 默认库/schema 为 null 时明确使用驱动默认或要求显式配置，并避免把合法默认目标
  当作越界。
- 审计使用实际执行目标（含默认回填后的 database/namespace），`rowCount` 优先取
  `rows` 长度（或统一结果的行数语义），每次调用生成 requestId，并在 UI 展示。

## `f1a94b2d1` 修复后复测（2026-11-06，仍失败）

`f1a94b2d1` 相对 `a0676c8f0` 只多展示审计 `namespace` 一列；Rust 的 SQL scope 和
schema resource 逻辑与 `a0676c8f0` 相同。用 `target/debug/datazen_desktop --mcp`
和隔离数据目录复测，以下问题仍在：

1. **`SHOW` 是 SQL scope 的绕过。** MySQL 允许库为 `mysql`、连接默认库为
   `mysql` 时，`query` 执行 `SHOW TABLES FROM datazen_demo` 返回 2 行；
   `SHOW DATABASES` 返回 40 行（包含 `datazen_demo` 等 scope 外库）；
   `SHOW CREATE TABLE datazen_demo.test_orders` 返回该表 DDL。审计把这三条记为
   `databaseName=mysql`、`decision=allow`，即 scope 外目标和审计目标都不正确。
2. **连接默认库为 null 时仍无法实际解析。** `conn_e2e_pg` 的 `database=null`、
   `schema=null`，配置 `mcpAllowedDatabases=["postgres"]` 后执行
   `SELECT 1 AS ok`，在 SQL 进入解析前报
   `MCP SQL scope: actual default database/schema could not be resolved:
   default target probe failed: ... has no database`。原因是默认目标探针走
   `read_target_command`，而该路径对默认库为 null 的多库驱动要求显式 database。
   schema 非 null/连接库已配置时 namespace 探针可工作。
3. **schema resource 允许后内容为空。** 允许库 `postgres`、namespace `public`，
   `resources/read` 读取 `datazen://schema/conn_e2e_pg/postgres` 不再报错，但
   `contents[0].text` 长度为 0；日志为
   `driver 'postgresql' has a schema level: an explicit schema is required`。
   `resources.rs` 已解析出有效 namespace，但 `connection_schema_context` 固定传
   `schema: null`，所以每张表的 schema 读取失败并被跳过。
4. **审计仍把 scope 外 SQL 记成默认库。** `SHOW ... datazen_demo` 成功执行后审计
   `databaseName=mysql`；普通跨库 `SELECT` 被拒绝时审计也记录默认库，而不是
   SQL 中尝试的 `datazen_demo`/`secret`。

本轮通过的部分：显式配置默认库后，MySQL `datazen_demo`/`information_schema`
和 PG `information_schema`/`pg_catalog` 的普通 `SELECT`、CTE、子查询、UNION、
JOIN、DML、`USE`/`SET`、解析失败和多语句均在执行前拒绝；PG schema 为 null 时
namespace 探针解析出 `public`；SELECT 审计 `rowCount` 与 `requestId` 正确；前端
requestId/namespace 展示和审批 Deny/Allow/timeout/cancel 不回归。Rust/前端回归
结果见 final report；因为上述 1–3 属于验收硬条件，BUG-017 不能改为“已验证”。

## `0006d30ca` 修复后复测（2026-11-06，仍失败）

`0006d30ca` 修复了前一轮的 SHOW、schema resource 和拒绝审计缺口，真实 MCP 黑盒
确认：

- MySQL 允许库 `mysql` 时，`SHOW TABLES FROM datazen_demo`、`SHOW DATABASES`、
  `SHOW CREATE TABLE datazen_demo.test_orders`、`SHOW COLUMNS/INDEX/TABLE STATUS`
  中的 scope 外目标均在执行前拒绝；`SHOW TABLES FROM mysql`、`SHOW COLUMNS FROM
  mysql.user`、`SHOW INDEX FROM mysql.user`、`SHOW CREATE TABLE mysql.user` 正常。
- PG 允许 `postgres` + `public` 时，`SHOW TABLES FROM information_schema` /
  `pg_catalog` 的 CREATE/INDEX 形式均在执行前拒绝；普通 `information_schema` /
  `pg_catalog` SELECT 也拒绝。
- 拒绝审计记录了 SQL 中尝试的 `datazen_demo` / `information_schema` / `pg_catalog`
  （SHOW DATABASES 这类无具体目标的形式仍只能记默认目标），allow/deny/read 均有
  requestId。
- schema resource `datazen://schema/conn_e2e_pg/postgres` 在 `postgres` + `public`
  scope 下返回非空 DDL（本轮 1547 chars）。

**仍未通过：**连接 `conn_e2e_pg` 的 `database=null`、`schema=null`，scope 为
`mcpAllowedDatabases=["postgres"]` 时，`query` 的 `SELECT 1 AS ok` 仍失败：

```text
Query step 'read-only-command' has no database: set `database` on the step,
or a workflow-level `database`, or a default database on connection 'conn_e2e_pg'
```

探针本身成功（审计行已是 `databaseName=postgres`、`namespace=public`、allow、
requestId），但 `crates/datazen/src/mcp/application/tools.rs` 构造 query 命令时只传
`sql`/`limit`，没有把解析出的 database 传给 `read_target_command`；桌面 mock 测试
的 `mcp_null_profile_defaults_are_probed_and_audited` 因 mock 不触发多库驱动的
`MissingDatabase` 而假通过，真实 PG 暴露了执行路径缺口。`database=postgres`、
`schema=null` 时同一 `SELECT 1` 可通过，说明问题仅在默认库为 null 的执行目标注入。

因为验收要求 2 明确要求该调用通过，BUG-017 保持“待修复”。
