### `open` 仍有真实可用性缺口

CLI 侧确实已经不再伪造 URI：`open_launches_desktop_with_argv_and_never_emits_a_uri`
用假的 `DATAZEN_DESKTOP_BIN` 验证了转发参数为
`--datazen-open-connection <id> --datazen-open-query <sql>`；缺失可执行文件返回
`E_NOT_FOUND`；桌面 `open_request` 解析单测也通过。新版桌面进程用测试 app bundle
启动后能完成启动并输出 `main window shown after page load`。

但实际可用性仍未闭环：

1. **桌面 App 已运行时，macOS 启动路径不会送达参数。**
   `crates/datazen-cli/src/desktop_launch.rs:89` 使用
   `/usr/bin/open -a <app> --args ...`；实测 app 已运行（PID 64792）时再次执行
   `open -a ... --args --datazen-open-connection ... --datazen-open-query ...`，
   `open` 返回 0，PID 仍是 64792，没有新进程启动。桌面只在
   `crates/datazen-desktop/src/bootstrap/run.rs:90` 启动时解析 argv，
   没有单实例 reopen/参数转发处理，因此已运行的常见场景下 CLI 的 `open`
   实际没有打开任何连接；`commands.rs:305` 仍无条件输出 `"launched": true`。
2. **`open --help` 仍是旧行为**：显示 “Print the descriptor an external opener can
   use for a connection”，和实际启动桌面不一致；`OpenArgs.query` 也没有帮助文本。
3. **`--data-dir` 没有转发给桌面**：`desktop_launch::launch` 只转发 connection id 和
   query。若 CLI 用 `--data-dir` 指向测试/临时目录，桌面仍读默认目录，会找不到同一
   连接，open 失败但 CLI 已报成功。
4. **前端事件→UI 未完成独立黑盒确认**：受本机屏幕录制/辅助功能权限限制，无法可靠
   读取 WebKit 窗口 DOM；本环境尝试把桌面前端指向 worktree 源构建也没有得到可验证
   的 UI 证据。不能把 helper 单测或“桌面进程启动”当作完整 open 验收。
5. **已连接 tab + query 的边界**：`ConnectionPage.tsx` 的 pending query effect 依赖
   `[tabs, allPanels]`；若目标连接已有 connected tab 且没有 panel，事件只设置
   `pendingOpenQueryRef`，tabs/allPanels 不变，`newQuery` 不会执行。首次打开新 tab
   的常见路径可用，但这是未覆盖的 residual。
6. **requestId 只用 query 长度**：`cli:<id>:<len>`，同连接两个等长不同 query 在同一
   进程内会碰撞，第二次被 dedupe 丢弃。

### shared execution Runtime 边界判断（不单独决定本次失败）

`RuntimeConnectionUseCases::new` 需要 `ProfileRepository`、`PolicyService`、
`SessionBackend`，这些是 Desktop 宿主对象，不在 `datazen-cli` 的依赖闭包内。CLI 目前
复用 connection 读取、`datazen-driver-api`、`sql_guard`，并对隧道 fail-closed；用
假 Repository 拼一个 Runtime 会违反仓库“不提交空壳/Dummy”的约束。

因此我的判断是：**若 T18 验收文字明确改成“CLI 仅复用 connection/driver-api/
sql_guard，不接 execution Runtime”，该边界可以非阻塞**；当前 T18/实现文档仍写
“复用共享 execution 端口”，按现有文字仍是未接项。它不是安全旁路，但不能自行把
边界声明当成“已验证”。

### `--limit` 新增边界失败（不能忽略）

```bash
# PostgreSQL dollar-quoted literal：值被篡改
target/debug/datazen --data-dir /tmp/t18b/desktop-data query conn_e2e_pg \
  'SELECT $$a;b$$ AS s -- limit' --limit 1 --timeout 5s --json
# {"rows":[["a LIMIT 2;b"]],"truncated":false}
# 原值应为 "a;b"；LIMIT 被插进了 dollar quote 内部，属于数据损坏。
```

```bash
# MySQL # 尾随注释：LIMIT 被注释掉，查询无界
target/debug/datazen --data-dir /tmp/t18b/desktop-data query conn_gimlk4k4 \
  'SELECT SLEEP(0.2) FROM information_schema.columns # tail' \
  --limit 1 --timeout 2s --json
# exit 10 / E_TIMEOUT，real 2.01s
```

`limited_sql` 的扫描器只识别 `--`、`/* */`、`'`、`"`、`` ` ``；没有 PostgreSQL
dollar quote、MySQL `#` 注释、SQL Server `[]`，也未处理反斜杠转义。MySQL `#` 前置
场景本次能通过（LIMIT 追加在有效 SQL 后），但尾随 `#` 会让追加的 LIMIT 进入注释。
这直接违反“limit 不破坏 SQL / 不产生数据损坏”的验收底线。

## 本轮修复（`fix: complete CLI open and limit edges`）

- `open` 改为启动真实桌面进程：CLI 传入
  `--datazen-open-connection <id> [--datazen-open-query <sql>]`，桌面启动时解析并
  发出 `datazen:open-connection`；前端打开连接，带 query 时在连接就绪后创建查询
  面板。macOS 用 `open -a`，Windows/Linux 用安装路径或 `DATAZEN_DESKTOP_BIN`；
  找不到应用返回 `E_NOT_FOUND`，不输出伪造 URI。
- `--limit` 改为注释感知扫描：前置空白/注释可跳过，尾随注释前追加 LIMIT，
  `WITH` 只在最终主语句为 SELECT 时追加，CTE DML 不追加，多语句逐条追加；补单测和
  真实 PG `pg_sleep` 计时。
- `PRAGMA main.table_info(...)` 等 schema 前缀只读形式放行；带 `=` 的赋值仍拒绝。
- shared execution Runtime 未接：`RuntimeConnectionUseCases::new` 需要
  `ProfileRepository`、`PolicyService`、`SessionBackend`，CLI 没有这些宿主对象；
  详见 `docs/features/ai-cli.md` 的装配边界。

## ed5a19d6e 历史阻塞（部分已被 d36080ce5 覆盖）

### 1. `open` 仍然不可用

```bash
./target/debug/datazen --data-dir /tmp/datazen-t18-p0 open local --json
# exit 14
# {"ok":false,"code":"E_UNSUPPORTED",
#  "message":"opening connection 'prod-db' from the CLI is not wired to a desktop route; no connection URI was emitted"}
```

现在不再伪造 `datazen://connection/<id>`，这是安全上的改进；但 T18 的实现清单包含
`open`，PRD §8.3 明确要求：

```text
datazen open <connection> --query "<sql>"
```

当前没有任何桌面连接路由或启动路径，命令永远返回 `E_UNSUPPORTED`。**失败关闭不能
替代功能实现**；若产品决定 T18 不做 `open`，必须先修改 T18/PRD 验收文字，否则仍是
阻塞项。临时测试 `open_does_not_emit_an_unconsumable_uri` 只断言“不输出 URI”，
没有覆盖“能打开”。

### 2. shared execution Runtime 仍未接

`crates/datazen-cli/src/query.rs:132-205` 仍直接：

```rust
let driver = create_driver(&config.database_type)?;
let handle = driver.connect(config).await?;
let result = driver.query(&handle, sql).await?;
```

`ensure_supported_host_wiring` 只对隧道配置 fail-closed，没有调用
`datazen::execution` Runtime、lease、session 或共享执行入口。T18 实现文档
`docs/development/ai-assistant-parity-implementation.md:438` 明确要求
“复用共享 connection/execution 端口”。

**判定**：不能以“共享 driver-api + sql_guard + fail-closed”完全替代 T18 的
execution 端口要求。fail-closed 解决了“静默直连绕过隧道”的安全问题，平台 vault
也补上了，但：
- 没有共享 Runtime 的会话/资源/租约语义；
- CLI 仍需自己直接组装驱动；
- 若未来共享执行加入取消、审计、连接生命周期，CLI 会再次分叉。

如果产品明确把 T18 改为“CLI 只复用 driver-api，不接 Runtime”，并同步验收文字，
该边界可以接受；按当前文字仍是阻塞项。

## ed5a19d6e 历史 `--limit` 边界（标准路径已在 d36080ce5 修复）

### 2.1 普通路径已通过

```bash
# 10 行 × 0.1s，limit 1：只执行 2 行，约 0.23s，rows=1 truncated=true
datazen --data-dir /tmp/datazen-t18-pg query pg \
  'SELECT i, pg_sleep(0.1) FROM generate_series(1,10) AS i' \
  --limit 1 --timeout 2s --json

# 100000 行 limit 5：rows=5 truncated=true
datazen ... query pg 'SELECT i FROM generate_series(1,100000) AS i' --limit 5 --json

# 已有 LIMIT 50、--limit 5：外层封顶，rows=5 truncated=true
datazen ... query pg 'SELECT i FROM generate_series(1,100) AS i LIMIT 50' --limit 5 --json
```

`live_databases` 中 `postgres_limit_is_pushed_into_execution` 也通过。

### 2.2 前置注释：limit 完全不追加，查询无界

```bash
/usr/bin/time -p datazen --data-dir /tmp/datazen-t18-pg query pg \
  '/* leading */ SELECT i, pg_sleep(0.2) FROM generate_series(1,10) AS i' \
  --limit 1 --timeout 2s --json
# exit 10 / E_TIMEOUT；real 2.01s（若 limit 生效应约 0.4s）
```

`limited_sql` 用 `trimmed.to_ascii_uppercase().starts_with("SELECT"/"WITH")` 判断；
`/* leading */` 使其判为非 SELECT，直接返回原 SQL（`query.rs:165-182`）。同样，
`-- leading\nSELECT ...` 也绕过（用 `--` 传 SQL 时实测 2.01s timeout）。

### 2.3 尾随行注释：追加的 LIMIT 被注释掉

```bash
datazen ... query pg \
  'SELECT i, pg_sleep(0.2) FROM generate_series(1,10) AS i -- trailing' \
  --limit 1 --timeout 2s --json
# exit 10 / E_TIMEOUT；real 2.01s
```

`limited_sql` 把 ` LIMIT 2` 追加到 `-- trailing` 之后，整段成为注释，实际仍是
无界查询。尾随块注释 `/* trailing */` 可以正常追加；行注释是明确回归。

### 2.4 `WITH ... UPDATE/INSERT/DELETE` 被错误追加 LIMIT

```bash
datazen ... query pg \
  "WITH x AS (SELECT 1) UPDATE datazen_t18_limit_probe SET note='w' WHERE id=2 RETURNING id" \
  --allow-writes --limit 1 --json
# exit 11 / E_DRIVER
# Query failed: syntax error at or near "LIMIT"
```

`append_select_limit` 把任何 `WITH` 当 SELECT；`limited_sql` 在其后追加 LIMIT，
`WITH ... UPDATE ... RETURNING` 不是 SELECT，语法被破坏。普通 `UPDATE`/`INSERT`/
`DELETE` 已实测正常，但“非 SELECT 不破坏”对 CTE DML 不成立。

## ed5a19d6e 历史判定

- **`open`：仍阻塞**。E_UNSUPPORTED 是诚实的 fail-closed，但不等于 T18/PRD 要求的
  `open` 可用；需要桌面连接路由/启动实现，或正式 descope。
- **shared execution Runtime：仍阻塞**。当前只共享了 connection、driver-api 和
  sql_guard；fail-closed 只能作为安全补丁，不能证明已复用 execution 端口。若产品
  明确修改验收文字为“CLI 仅共享 driver-api”，可作为边界接受。
- **`--limit`：普通路径已修复，但注释/CTE 边界仍失败**；这是本轮新增的独立失败，
  不能标“已验证”。
- SUGGESTED 修复（不修改生产代码）：limit 追加前先剥离/保留前后注释并识别实际主
  动词；对 `WITH` 用 SQL 主语句判断而非前缀；阅读器/解析器应保留行注释分隔；补
  `--limit` 前后注释、`WITH UPDATE RETURNING`、`PRAGMA main.table_info` 测试。
