# BUG-016 T18 生产库 PRAGMA 可写、`--limit` 不约束执行、`open` 描述符不可消费，且 CLI 未接共享执行/隧道/平台 vault

- 关联任务：T18 CLI 与 Agent Skill
- 被测提交：`16f2cce89`（`feat: add datazen CLI and agent skill`）
- 严重度：阻塞 T18 验收（生产库写保护可绕过；`--limit` 只截断结果、不限制执行；`open` 的 URI 不是桌面可消费的 deep link；T18 明确要求的共享 execution 端口、隧道和平台凭据路径未装配）
- 状态：未修复（独立复测发现）

## 结论

T18 的 `doctor`、`capabilities`、`connections`、`schema`、`query`、`context`、JSON/CSV、
`--file`、`--timeout`、默认只读、DML 双 flag、DML 生产拒绝、`agent setup` 和 Skill
安装均已实测可用；`cargo test -p datazen-cli` 的 20 个单元测试和 9 个真实二进制
集成测试也全部通过。但以下四项不能由现有测试覆盖，且不满足 T18 验收：

1. **生产库仍可被 `PRAGMA` 写穿。** `PRAGMA journal_mode=WAL` 带两个 flag 在
   `prod-db` 上返回成功，并真实改变 SQLite 数据库；`--allow-writes` +
   `--allow-dangerous-sql` 对生产库不是“始终拒绝写”。
2. **`--limit` 不进入执行层。** 它只在驱动返回完整结果后截断 `rows`；对
   `pg_sleep` 查询使用 `--limit 1 --timeout 2s` 仍运行完整 10 行并在 2.03s
   返回 `E_TIMEOUT`。Agent 仍可触发无界查询。
3. **`open` 输出的 URI 不是桌面可消费的 deep link。** `datazen://connection/local`
   没有 publisher-dot 的 wapp host，桌面 `parse_datazen_uri` 直接判为非法；没有
   连接打开路由，也没有 GUI 启动路径。
4. **CLI 没有复用共享 execution 端口。** `query.rs` 直接 `create_driver` 后调用
   `DatabaseDriver::connect/query`，绕过 `datazen::execution` Runtime；因此
   `sshTunnel`/`tunnelId` 被静默忽略（实测无效 SSH 隧道仍直连成功），默认桌面
   `PlatformVault` 主密钥也不可读（真实 app data 的 `keyBackend` 为 `unavailable`）。
   `docs/features/ai-cli.md:104-106` 已把隧道/platform vault 写成“边界”，但这与
   T18 实现要求“复用共享 connection/execution 端口”和 PRD “认证复用应用数据目录/
   OS keychain”冲突。

## 独立复现

环境：worktree `16f2cce89`，macOS，CLI 二进制 `target/debug/datazen`；临时数据目录
`/tmp/datazen-t18-fixture`（本次测试创建，未进入仓库）。

### 1. 生产 `PRAGMA` 写入

连接 `prod-db` 的名称命中生产识别（`query.rs::is_production`），SQLite 文件为
`/tmp/datazen-t18-fixture/test.db`：

```bash
./target/debug/datazen --data-dir /tmp/datazen-t18-fixture \
  query prod-db 'PRAGMA journal_mode=WAL' \
  --json --allow-writes --allow-dangerous-sql
# exit 0
# {"connection":"prod-db","columns":["journal_mode"],"rows":[["wal"]], ...}
```

对照：

```bash
# DML 被正确拒绝：exit 9 / E_PRODUCTION_WRITE
./target/debug/datazen --data-dir /tmp/datazen-t18-fixture \
  query prod-db 'INSERT INTO items(name) VALUES ("x")' \
  --json --allow-writes --allow-dangerous-sql
```

原因在 `crates/datazen-cli/src/query.rs:184-199`：

```rust
let write = check_sql(&normalized, true, false).is_err(); // PRAGMA 在 READ_VERBS 中，返回 Ok
let dangerous = tokens.iter().any(|token| is_dangerous_keyword(token)); // PRAGMA 为 true
if write && is_production(config, safety.production) { ... } // write=false，生产检查不触发
```

`PRAGMA` 随后只受“危险语句需要两个 flag”约束；两个 flag 都给出时直接执行。
`check_sql` 的写动词表（`crates/datazen/src/execution/domain/sql_guard/safety.rs:105-110`）
不含 `PRAGMA`，而 `PRAGMA journal_mode=WAL` 会持久改变数据库头/日志模式，不是只读
语句。现有单元测试
`production_refuses_writes_even_with_both_flags`（`query.rs` 测试区）只覆盖
DML，因此没有发现该旁路。

这不是“打印了危险但没执行”：返回的 `journal_mode` 为 `wal`，数据库状态已改变。
同样可写路径还包括 `PRAGMA user_version=...` 等；在只读连接上会被 `read_only`
分支拦下，但生产连接通常不是 `readOnly`，所以两个 flag 即可。

### 2. `--limit` 只截断结果，不限制数据库执行

```bash
/usr/bin/time -p ./target/debug/datazen --data-dir /tmp/datazen-t18-fixture \
  query pg 'SELECT i, pg_sleep(0.5) FROM generate_series(1,10) AS i' \
  --limit 1 --timeout 2s --json
# exit 10 / E_TIMEOUT，real 2.03s
# query exceeded the 2 second timeout
```

若 limit 下推到 SQL，10 行每行 0.5s 的查询应只执行 0.5s 后返回 1 行；实际执行
完整 5s，超时才中止。代码路径：

- `DriverExecutor::execute` 只把 `request.sql` 交给驱动，完全忽略 `request.limit`
  （`crates/datazen-cli/src/query.rs:128-133`）；
- `QueryOutput::from_result` 在驱动已返回所有行后才 `rows.truncate(limit)`，并设置
  `truncated`（`query.rs:49-52`）。

现有集成测试 `query_limit_and_csv_output_are_parseable`
（`crates/datazen-cli/tests/cli.rs:151-174`）只断言输出为 `"n\n1\n"`，没有断言
执行行数/耗时，因此测试通过不等于 limit 生效。

### 3. `open` 描述符不可消费

```bash
./target/debug/datazen --data-dir /tmp/datazen-t18-fixture open local --json
# {"connection": {...}, "note":"hand this descriptor to the DataZen desktop app; ...",
#  "uri":"datazen://connection/local"}
```

临时 Rust 断言（已删除）直接调用公共解析器：

```rust
assert!(parse_datazen_uri("datazen://connection/local").is_err());
```

结果通过（即确实非法）。`crates/datazen/src/wapps/protocol.rs:78-82` 要求 host 是
`<publisher>.<name>` 的 wapp id；`connection` 没有 publisher dot，被拒绝为
`invalid wapp host`。桌面协议处理器只把合法 URI 交给 `route_datazen_request` 的
wapp 路由，没有 `datazen://connection/<id>` 分支；CLI 也不启动 GUI
（`commands.rs:302-316` 只输出 JSON）。因此用户按文档把描述符交给桌面 App 时会得到
404/非法 URI，而不是打开连接；`--query` 只是把 SQL 放进 query string，没有任何
执行或安全复核入口。

### 4. 未复用共享 execution 端口，隧道/平台 vault 未装配

`query.rs:135-157` 直接：

```rust
let driver = create_driver(&config.database_type)?;
let handle = driver.connect(config).await?;
let result = driver.query(&handle, sql).await?;
```

没有经过 `datazen::execution` 的 Runtime/lease/资源端口，也没有桌面隧道装配。
独立验证：给 PG 连接加上 `sshTunnel.enabled=true`、`sshTunnel.port=1`、
`tunnelId=nonexistent-tunnel` 后，CLI 仍成功执行 `SELECT 1`，证明它没有尝试隧道，
而是直接连 `host:port`（本机 PG）：

```bash
./target/debug/datazen --data-dir /tmp/datazen-t18-fixture query pg 'SELECT 1 AS n' --json
# exit 0，rows [[1]]；无效 SSH 隧道被静默忽略
```

凭据边界同样不是完整的桌面路径：

- 真实默认 app data `~/Library/Application Support/com.tbeasy.datazen` 没有 `.key`；
  `doctor` 返回 `keyBackend: "unavailable"`，`connectionCount: 12`；
- `app_data.rs:61-72,140-151` 只支持存在 `.key` 的文件后端，或显式
  `DATAZEN_KEYRING=keyring`；默认桌面的 `PlatformVault`（macOS security CLI /
  Windows DPAPI，见 `crates/datazen-desktop/src/store/key_backend.rs:16-23`）未实现；
- 没有 `.key` 时，加密凭据的 query/schema 返回 `E_CREDENTIAL`，即使桌面 App 本身
  可以正常解密连接。

`docs/features/ai-cli.md:104-106` 把这写成明确的宿主装配边界；如果产品接受该边界，
应修改 T18/PRD 的验收文字。但按当前 T18 实现要求，它不是“共享 execution 端口”的
实现，默认桌面凭据也不可用。

## 已通过项（不能抵消上述阻塞）

- 命令主体：`doctor`、`capabilities`、`connections`、`schema`、`query`、`context`
  均返回可解析 JSON；`connections` 不输出密码/token；`--file` 与 `--csv` 可解析。
- 安全主体：默认写返回 `E_READ_ONLY`/exit 6；`--allow-writes` 单独允许 DML；
  DDL 单独 `--allow-writes` 返回 `E_DANGEROUS_SQL`/8；单独
  `--allow-dangerous-sql` 返回 `E_WRITE_FLAG`/7；DML 生产双 flag 返回
  `E_PRODUCTION_WRITE`/9；`readOnly` 连接写返回 6；未知连接 4；歧义名称 2；
  `--json --csv` 返回 `E_OUTPUT`/13；无密钥 `E_CREDENTIAL`/5。
- `--timeout` 在 PG `pg_sleep(2)` 上 100ms/2s 都返回 `E_TIMEOUT`/10；`--file`
  写入 JSON/CSV 成功；JSON/CSV 均可由 Python 解析，CSV 正确处理逗号/引号。
- `open` 退出 0 且 JSON 结构完整，但 URI 语义失败（见上）。
- `agent setup` 在临时 HOME 安装到 `~/.agents/skills/datazen/SKILL.md`，第二次返回
  `alreadyInstalled` 且不覆盖用户文件；临时 T17 `SkillCatalog` 测试确认
  `id=user:datazen`、`name=datazen`、`use_skill` 可见。
- 真实 PG/MySQL 直连：`schema`/`query` 在本机 PostgreSQL 5432、MySQL 3306 上返回
  正确表与行；因此“只有 SQLite 被 live 测试”本身不是本轮 `query` 的功能阻塞，但
  自动化测试仍只覆盖 SQLite，PG/MySQL 是本次人工补测。
