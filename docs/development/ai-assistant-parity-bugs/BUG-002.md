# BUG-002 T02 新增 chat_logs_persisted_connection_id 在并行测试下间歇失败

- 关联任务：T02 稳定连接身份与会话 key
- 被测提交：`ceaa7f0622c34a273df2f59b32e02cc3b492a4df`
- 严重度：阻塞 T02 验收（任务指定的验收命令约 30% 概率失败）
- 状态：已验证

## 现象

运行任务指定的验收命令：

```bash
cargo test -p datazen --features ai --lib ai::application::chat_session::tests
```

新增测试 `ai::application::chat_session::tests::chat_logs_persisted_connection_id` 间歇性失败，失败时其余 10 个测试全部通过：

```text
---- ai::application::chat_session::tests::chat_logs_persisted_connection_id stdout ----

thread 'ai::application::chat_session::tests::chat_logs_persisted_connection_id' panicked at crates/datazen/src/ai/application/chat_session_tests.rs:383:5:
ai_chat log must carry the persisted connection id:
```

断言消息中的 `logged` 为空串，说明 `Capture` layer 没有收到任何事件；不是字段值不匹配，而是事件完全没有到达捕获层。

## 复现

```bash
cd .worktrees/datazen-ai-assistant-parity
for i in $(seq 1 20); do
  cargo test -p datazen --features ai --lib ai::application::chat_session::tests
done
```

本机实测 20 次中第 3、4、5、10、12、17 次失败（6/20）；失败退出码 `101`。同一命令加 `-- --test-threads=1` 连续 5 次全部通过；单独过滤该测试（`...::tests::chat_logs_persisted_connection_id`）也通过。失败与并行执行/测试调度相关，而不是日志字段没写。

## 期望

默认并行执行（CI 与协调者验收使用的同形命令）下该测试稳定通过；测试结果不应依赖测试线程调度顺序或 tracing 的全局状态。

## 实际

并行执行时偶发 `Capture` 收不到 `run_chat_session` 的 `tracing::info!("ai_chat: start")` 事件，`events` 为空；单线程或单测运行时稳定通过。

## 位置

- `crates/datazen/src/ai/application/chat_session_tests.rs:316-388`（本 commit 新增的测试）
- `crates/datazen/src/ai/application/chat_session.rs:79-89`（被断言的 `ai_chat: start` 日志）

## 初步根因

tracing 的 callsite interest 是**全局缓存**：某个 callsite 第一次被调用时，按“当时已注册的 dispatcher”计算 `Interest`；`tracing-core` 在没有 dispatcher 时回退为 `Interest::never`：

```rust
// tracing-core/src/callsite.rs
let interest = interest.unwrap_or_else(Interest::never);
callsite.set_interest(interest)
```

若本测试的 `with_default(subscriber, ...)` 之前，另一个并行测试已经调用过 `run_chat_session`（没有 subscriber），该 callsite 会被缓存为 `never`。之后本测试安装线程本地 Capture 时，`with_default` 不会重建既有 callsite 的 interest（`Dispatch::new` 只做 `register_dispatch`，不调用 `rebuild_interest_cache`），于是 `info!` 被静态短路，Capture 永远收不到事件。单线程时本测试通常是该 callsite 的首个调用者，interest 在 subscriber 安装之后才计算，因此稳定通过。

## 建议

- 在该测试 `with_default` 内、调用 `run_chat_session` 之前调用 `tracing::callsite::rebuild_interest_cache()`（tracing 0.1 的 `callsite` 是 doc-hidden re-export），强制按当前已注册 dispatcher 重算 interest；或
- 改为测试二进制级一次性安装的全局 capture subscriber，按 `request_id` 过滤断言，避免线程本地 dispatcher 与全局 interest 缓存的竞态；或
- 若目标只是验证日志字段，可把“开始日志字段组装”抽成可单测的纯函数，绕开 tracing 全局状态。
- 修复后必须在默认并行参数下重复运行（建议 ≥20 次）确认稳定，不能靠 `--test-threads=1` 规避。
