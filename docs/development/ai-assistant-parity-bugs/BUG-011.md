# BUG-011 T13 Memory 设置页使用原生 `<select>`，且关闭记忆后仍可直接创建 candidate

- 关联任务：T13 Memory 设置、列表、候选 UI
- 被测提交：`fd039d7a0`（`feat: add AI memory settings and management UI`）
- 严重度：阻塞 T13 验收
- 状态：待修复

## 结论

T13 的主功能（设置、默认关闭、列表、候选、导出、Chat remember/toast）大部分通过，但有两个阻塞问题：

1. **前端全量门禁新增失败**：`MemorySection.tsx` 在 4 处使用原生 `<select>`，违反仓库既有 `noNativeSelect` 规则；全量 Vitest 因此新增 1 个失败测试。T13 的 42 文件定向集不包含该门禁，所以定向测试全绿不能代表可交付。
2. **关闭记忆后仍可直接产生 candidate**：默认配置 `memory.enabled=false` 时，`ai_memory_create` 传 `status: "candidate"` 仍成功写入；`Chat` 的“记住这条”在前端被拦截，但后端 IPC 没有按总开关拒绝，和“关闭后不产生候选 / 关闭时 create candidate 被拒绝”的验收要求不一致。

## 证据

### 1. 原生 select 门禁

单独复跑：

```text
pnpm vitest run packages/frontend/src/lib/__tests__/noNativeSelect.test.ts
```

结果：

```text
AssertionError: replace with components/ui/Select: expected [ Array(1) ] to deeply equal []
Received: [ "windows/settings/MemorySection.tsx" ]
Tests  1 failed (1)
```

`packages/frontend/src/windows/settings/MemorySection.tsx` 的原生 select 行：

- `:267` 云 Provider 策略
- `:353` 连接筛选
- `:367` 类型筛选
- `:381` 状态筛选

全量 Vitest：

```text
Test Files  13 failed | 778 passed (791)
Tests       9 failed | 8169 passed (8178)
```

其中 `noNativeSelect` 是 T13 新增的失败；其余失败仍是既有的 desktop 平台夹具、`ci-tauri-build`、`check-driver-type-isolation`、`resolve-pro` 等环境/基线问题。前一提交 T12 的全量基线为 12 failed files / 8 failed tests，本次多出 1 个失败文件/测试。

### 2. 关闭记忆仍可创建 candidate

`crates/datazen/src/ai/domain/types.rs` 中 `AiMemorySettings::default()` 为 `enabled=false`。`crates/datazen-desktop/src/commands/ai/memory.rs:490` 的 `ai_memory_create` 没有读取 `resolve_memory_settings`，也没有按 `enabled` 拒绝 `candidate`。

临时独立 Rust 探针（已还原，不在提交中）：

```rust
let mut candidate = input("disabled candidate", "must not be stored");
candidate.status = Some(MemoryStatus::Candidate);
let result = ai_memory_create(app.state(), candidate).await;
assert!(result.is_err(), "disabled memory must not create a candidate");
assert_eq!(list_all(&app).await.total, 0);
```

实际结果：

```text
disabled memory must not create a candidate
test result: FAILED
```

即关闭状态下 `ai_memory_create(candidate)` 返回成功并落库。前端 `AiChatPanel` 的“记住这条”确实被 `settingsConfig.memory.enabled` 拦截（`AiChatPanel.test.tsx` 的禁用用例通过），但后端 IPC 仍是可写入的旁路。

## 影响

- T13 无法通过仓库的完整前端门禁；原生 select 与项目统一 `components/ui/Select` 约定冲突，也破坏主题/可访问性一致性。
- “关闭后不产生候选”只在 Chat 前端路径成立；任何直接调用 `ai_memory_create` 的渲染逻辑都能在关闭状态写入 candidate，违反验收语义。
- 记忆检索/注入本身在关闭时仍被强制 off；当前问题不是检索泄漏，而是候选写入和 UI 门禁。

## 建议修复方向（tester 未改代码）

- 将 `MemorySection.tsx` 的云策略、连接、类型、状态选择器替换为 `components/ui/Select`，并同步测试查询；随后复跑 `noNativeSelect` 与全量 Vitest。
- 在 `ai_memory_create` 入口读取 `resolve_memory_settings`；按验收要求拒绝 `status=candidate`（以及“记住这条”对应来源）在 `enabled=false` 时写入。若产品明确允许关闭状态下手工管理写入，应把“关闭后不产生候选”改写为仅约束 Chat/自动学习，并在验收中写明该例外。

## 非阻塞观察

- `autoLearn` 目前只有设置项，没有候选抽取的真实生产者；T13 只要求设置 UI，自动学习行为属于 T14 范围。
- 全量 Vitest 的其余失败为既有环境/基线问题，不应被算作 T13 回归；但 `noNativeSelect` 是本次新增，必须修复。
