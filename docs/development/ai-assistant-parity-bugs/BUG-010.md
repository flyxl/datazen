## 初始缺陷

T12 的后端能力和 Chat 展示组件基本完成，但**真实前端入口没有把 Memory 参数送进请求**：

1. `Nl2SqlPanel` 的 `generateSql` 调用只传 `dbSessionId/database/currentTable/contextFiles/contextTables`，没有 `connectionId`、`memoryMode`、`memoryScope`；面板本身也没有 `connectionId` prop。父级 `QueryEditorSection` 明明已持有 `connectionId`，却没有传给面板。
2. `AiChatPanel` 的 `sendChatMessage` 调用同样没有 `memoryMode` / `memoryScope`。Chat 的 `connectionId` 已传，但缺少模式字段时后端 `unwrap_or_default()` 落到 `MemoryMode::Off`，因此真实 Chat 永远不检索、不注入，也不会产生 `memory_used` chip。
3. NL2SQL 的流处理分支 `handleStreamChunk` 只累积 SQL，直接丢弃 `payload.memoryUsed`；`Nl2SqlState` 也没有 memory 字段。即便后端以后收到模式并返回引用，NL2SQL 前端目前也不会保存或展示。
4. 现有测试没有覆盖真实入口：`Nl2SqlPanel.test.tsx` 断言的正是**不含** Memory 字段的旧调用；`aiStore.test.ts` 只是手工给 store 传 `memoryMode/memoryScope`，没有经过面板。Chat chip 测试也是直接构造已带 `memoryUsed` 的 message。

### 真实入口

- `Nl2SqlPanel` 现在接收 `connectionId?: string`，并声明 `memoryMode?: 'off'|'ask'|'auto'`（默认 `auto`）、`memoryScope`（默认 `user`）。`generateSql` 调用实际发送 `connectionId/memoryMode/memoryScope`；`QueryEditorSection` 把已有的 `connectionId` 传给面板。
- `AiChatPanel` 同样声明默认 `auto/user`，普通发送 `sendMessage` 和“回答 assistant questions”的追问 `sendMessage` 都发送 `memoryMode/memoryScope`。原有普通发送测试与新增临时追问探针均通过。
- `Nl2SqlPanel.test.tsx` 不再只断言旧调用，而是用 `connectionId="conn-1"` 断言 `connectionId + memoryMode:auto + memoryScope:user`；`aiStore.test.ts` 另有 store → command 的透传断言。

### NL2SQL memoryUsed 与 UI

- `Nl2SqlState` 增加 `memoryUsed: AiMemoryReference[]`，初始 `[]`；`generateSql` 开始时重置为 `[]`，重新生成不会残留上一轮引用。
- `streaming.ts` 的 NL2SQL 分支保存 `payload.memoryUsed`；后续空 chunk 使用 `nl2sql.memoryUsed` 兜底，不覆盖首 chunk 的引用。
- `Nl2SqlPanel` 渲染 chip、展开列表和 `[M1]` 引用按钮；`focusMemory` 会展开、`scrollIntoView` 并聚焦目标项。独立临时探针验证了空 chunk 保留、重新生成清空、展开、聚焦和 `scrollIntoView`（临时测试已还原，未留在提交中）。

### 后端回归

- `chat_auto_injects_memory_and_emits_reference_chunk`、`chat_off_and_ask_never_inject_memory`、`strict_cloud_retrieval_excludes_internal_memories` 均通过。
- 当前修复提交无 Rust 变更；独立临时探针再次直接调用 `ai_generate_sql(Auto, User)`，捕获 `memoryUsed`、`<memory>` prompt 和 `inject` 审计，结果通过。

## 证据（初始缺陷）

### NL2SQL 调用点

`packages/frontend/src/components/ai/Nl2SqlPanel.tsx:58`：

```ts
void generateSql({
  dbSessionId,
  database,
  currentTable,
  contextFiles: ...,
  contextTables: ...,
});
```

`Nl2SqlPanelProps` 仅有 `dbSessionId/database/currentTable/onSqlChange`（同文件 19–25 行）；`QueryEditorSection.tsx:607` 只传了 4 个 props，`QueryEditorSection` 自身已有 `connectionId`。

`packages/frontend/src/stores/ai/types.ts:89` 和 `commands/ai.ts:110` 都**已经**声明可选的 `connectionId/memoryMode/memoryScope`，说明不是类型层缺口，而是调用层遗漏。

### Chat 调用点

`packages/frontend/src/components/ai/AiChatPanel.tsx:278` 的 `sendMessage({...})` 没有 `memoryMode`/`memoryScope`；`sendChatMessage` 的实现（`stores/aiStore.ts:424`）和 `ai_chat` 类型（`commands/ai.ts:149`）都支持这两个字段。

后端 `ai_chat` 在缺省时使用 `memory_mode.unwrap_or_default()`，而 `MemoryMode::default()` 是 `Off`（`crates/datazen/src/ai/memory/domain.rs:289`）。因此从真实 Chat UI 发出的每一轮都是 Off，T12 的“auto 才注入 / Chat chip”没有可达路径。

### NL2SQL 丢弃引用

`packages/frontend/src/stores/ai/streaming.ts:133` 的 NL2SQL 分支只处理 `content`/`done`，没有读取 `payload.memoryUsed`；`Nl2SqlState`（`stores/ai/types.ts:25`）也没有 `memoryUsed`。

### 后端不是问题

独立临时探针（已还原，不在提交中）直接调用 `ai_generate_sql`，传 `connectionId=Some(...)`、`memoryMode=Auto`、`memoryScope=User`，并创建一条 user scope 记忆：

- 捕获到 `ai:stream-chunk` 的 `memoryUsed`，含 `reference=M1`、subject、scope、score；
- provider 请求 system prompt 含 `<memory>` 和目标内容；
- `list_ai_memory_audit` 出现 `inject`。

同一探针用不匹配的查询文本时没有注入，说明检索本身按查询过滤，不是后端失效。该临时探针已删除，`memory_tests.rs` 已恢复原状。

## 初始影响（已消除）

- T12 目标“把 Memory 接进真实 Chat/NL2SQL 请求与流式响应”未达成；真实 UI 始终 Off，不会检索、不会注入、不会审计，Chat chip 没有真实来源。
- T12 NL2SQL 的 `connectionId` 缺失还会使 connection/database 级记忆无法按稳定连接身份命中。
- 后端 IPC、领域检索、注入策略、Chat chip 展示本身通过；该缺陷是**前端入口接线**，不是后端 Memory 逻辑失败。
