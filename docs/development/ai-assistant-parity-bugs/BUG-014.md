# BUG-014 T16 新兼容预设的 validate_config 只依赖 /models，缺少 Custom 的 probe 回退

- 关联任务：T16 Provider 预设扩展
- 被测提交：`5725fdfef`（`feat: add AI provider presets`）
- 严重度：高（OpenAI Compatible / Anthropic Compatible 仅实现 chat/messages 的端点会被验证误报为不可用）
- 修复提交：`b10c423e7`（`fix: probe compatible providers when models endpoint is unavailable`）
- 状态：已验证（`b10c423e7`）

## 结论

T16 的 10 个预设、协议路由、旧配置兼容和 key 日志检查均通过，但新增的
`CompatibleProvider::validate_config` 只调用 `/models`，没有复用
`CustomProvider` 已有的 probe 回退：

- `crates/datazen/src/ai/providers/custom.rs:161-185` 先尝试模型列表，失败后按协议
  调用 `openai_chat::probe` / `anthropic::probe`；
- `crates/datazen/src/ai/providers/compatible.rs:150-173` 对
  `CompatibleKind::OpenAiChat` 直接 `openai_chat::fetch_models(...).await?`，对
  `CompatibleKind::Anthropic` 直接 `anthropic::fetch_models(...).await?`。

因此同一个只实现 `/chat/completions`（或 `/v1/messages`）、不实现模型列表的兼容端点：

- 选旧 **Custom + open_ai_compatible**：验证走 probe，成功；
- 选新 **OpenAI Compatible**：验证停在 `GET /models`，返回 404/501，失败；
- **Anthropic Compatible** 同理（`GET /v1/models` 失败）。

聊天本身不经过 `validate_config`，所以 `initialize` + `complete` 仍可用；但设置页的
“验证”按钮会对有效配置给出假阴性，并与 T16 之前 Custom 的行为不一致。

## 独立复现

临时 Rust 测试（已删除）使用 wiremock：

- `GET /v1/models` → 501；
- `POST /v1/chat/completions` → 200。

结果：

```text
CUSTOM RESULT: Ok(())
COMPATIBLE RESULT: Err(RequestFailed("HTTP 501 Not Implemented: provider request failed (response body omitted; 0 bytes)"))
```

复现命令（当时）：

```bash
cargo test -p datazen --features ai --test t16_validate_temp -- --nocapture
# 1 passed：断言 Custom 成功、Compatible 当前失败
```

对照代码：

- `custom.rs:161-185` 有 `fetch_remote_models_with_client(...) -> Err(_) => probe`；
- `compatible.rs:165-172` 没有该 fallback。

## 影响

- T16 “OpenAI Compatible / Anthropic Compatible 真实可选”不完整：验证按钮对大量
  仅实现 chat/messages 的兼容服务不可用，用户容易误判“配置或 key 错误”。
- 这是相对旧 Custom 路径的行为回归：同样的端点/协议从 Custom 迁到新预设后验证失败。
- “拉取模型”按钮本身仍要求 `/models`，这是模型发现能力限制；但验证不应以模型列表
  存在为前提，尤其 `CustomProvider` 已明确采用 probe 回退。

## 修复方向（仅记录，不在本次测试修改）

1. `CompatibleProvider::validate_config` 复用 `CustomProvider` 的策略：先尝试
   `fetch_models`，失败后按 `CompatibleKind` 调用
   `openai_chat::probe` / `anthropic::probe`，再返回结果。
2. 补 wiremock 单测：`GET /models` 501 + `POST /chat/completions` 200（OpenAI chat）；
   `GET /v1/models` 501 + `POST /v1/messages` 200（Anthropic Messages）。
3. 保留现有模型列表成功路径，避免把 401/无效 key 的探测错误吞掉。

## 修复验证（`b10c423e7`）

修复仅改 1 个文件，属于 T16：

- `crates/datazen/src/ai/providers/compatible.rs`（+160/−7）

行为：

- 优先调用本协议的 `/models`；成功直接返回。
- `/models` 只有 `InvalidApiKey` / `RateLimited` 视为确定错误，原样返回。
- 404/501/5xx 及其他非鉴权错误回退到对应协议的 probe：
  - `CompatibleKind::OpenAiChat` → `openai_chat::probe`（`/chat/completions`）；
  - `CompatibleKind::Anthropic` → `anthropic::probe`（`/v1/messages`）。
- 不把 401 的 `/models` 错误用 probe 200 掩盖，也不把 429 降级成普通请求失败。
- 新增 wiremock 覆盖：404/501 回退（OpenAI 系 4 个类型、Anthropic Messages）、
  models 401 不被 probe 200 掩盖、probe 401/500 正确 Err。

独立临时 wiremock（已删除）额外补测：

- 400/403/404/500/501/503：OpenAI 系与 Anthropic 系均回退到正确协议；
- models 401 → `InvalidApiKey`，models 429 → `RateLimited`，均不被 probe 200 掩盖；
- probe 401 → `InvalidApiKey`、probe 500 → `RequestFailed`，两协议均验证；
- 错误文本不含测试 key；
- 旧 Custom `open_ai_compatible` 与 `anthropic` 协议回退均通过。
