# BUG-023 T24 apply_write 允许只读 SQL 执行，且 applied 回执/审计缺少 rowCount

- 关联任务：T24 写入提案与精确确认
- 被测提交：`d79466e2`（`feat: add confirmed write proposals`）
- 复测时间：2026-11-07
- 严重度：阻塞 T24。只读 SQL 穿过写入授权并被执行；审计缺少验收要求的 rowCount。
- 状态：待修复

## 结论

T24 的 token 绑定、一次性、过期、篡改拒绝、生产库/只读连接保护、Agent 只提案、
UI 精确确认、审计不含 SQL 等主路径通过。但发现两个独立缺陷：

1. `propose_write`/`apply_write` 没有校验 SQL 必须是写语句。`SELECT * FROM users`
   可以生成提案并获得一次性 token；`apply_write` 通过 `execute_target("execute")`
   实际执行该 SELECT，违反“只读语句永不执行”。
2. `applied` 回执和审计的 `rowCount` 对真实 `MultiQueryResult` 形状恒为 `None`：
   驱动返回 `{ "results": [ { "rowsAffected": 0, ... } ], "totalTimeMs": 0 }`，
   而 `affected_rows` 只检查顶层 `rowsAffected`/`rowCount`/直接数组，未进入
   `results`，导致 UI 显示 0、审计 `row_count=null`。

## 复现 1：只读 SQL 被执行

Store 级最小复现：

```text
propose("SELECT * FROM users", config(read_only=false), safe_mode=false)
apply(exact token/connection/database/SQL)
=> Ok(AppliedWrite { proposal.sql: "SELECT * FROM users" })
```

宿主级复现（临时测试）：

```rust
let proposal = propose_write_for_state(&state, "write-select", Some("app"),
    "SELECT * FROM users", None).await.unwrap();
let receipt = apply_write_for_state(&state, &proposal.token,
    "write-select", "app", "SELECT * FROM users").await;
```

实际 `apply_write_for_state` 返回 `Ok(AiApplyWriteReceipt)`，Mock 驱动
`execute_calls() == 1`，结果含：

```json
{
  "results": [
    {
      "sql": "SELECT * FROM users",
      "columns": [], "rows": [],
      "rowsAffected": 0, "executionTimeMs": 0, "truncated": false
    }
  ],
  "totalTimeMs": 0
}
```

根因：`WriteProposalStore::apply` 只调用
`sql_guard::check_sql(&sql, config.read_only, safe_mode)`；该函数在
`!read_only && !safe_mode` 时直接返回 `Ok(())`，从不判断 SQL 是否为写语句。
`propose` 同样只做非空/大小校验。因此 SELECT 从未被拒绝。

影响：写入确认通道可以执行任意只读查询，绕过查询工具的 LIMIT/结果大小策略；
用户以为在确认写，实际执行了未受写入语义约束的读取。也违反“非只读 SQL 走提案”。

## 复现 2：applied rowCount 丢失

对 `UPDATE users SET role = 'admin' WHERE id = 42` 走完整 propose/apply：

```text
receipt.row_count == None
receipt.result == {
  "results": [ { ..., "rowsAffected": 0 } ],
  "totalTimeMs": 0
}
audit applied.row_count == None
```

根因：`crates/datazen-desktop/src/commands/ai/write.rs::affected_rows` 只检查
顶层 `rowsAffected`、`rows_affected`、`affectedRows`、`affected_rows`、`rowCount`
和直接数组的首行，未检查 `data["results"][*]["rowsAffected"]`。真实驱动
`execute` 返回的是 `MultiQueryResult`（如上面的 `results` 数组），所以恒为
`None`。

影响：违反“审计 proposal/applied/denied 含 rowCount”；UI 的 applied 回执把
`null` 显示成 0，用户无法核对影响行数，审计也无法复核。

## 修复建议

- 在 `propose` 和 `apply` 都强制“写语句”分类：拒绝纯 SELECT/SHOW/EXPLAIN 等
  只读语句；`apply` 在任何 `execute_target` 之前再次拒绝，不能只依赖
  `check_sql` 的连接级 read_only/safe_mode。
- 明确多语句策略：若允许写多语句，至少拒绝含只读语句的混合提案，或逐条分类。
- `affected_rows` 支持 `MultiQueryResult` 的 `results` 数组；按语句汇总
  `rowsAffected`（或定义首条/总和），确保回执与 applied 审计为 `Some(n)`。
- 测试真实 `MultiQueryResult` 形状，而不只测顶层 `rowsAffected`。
