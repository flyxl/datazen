## 7. 结论与建议

**wave/number-order 执行不安全。** 621 个 remaining 任务之间存在 2722 条依赖边，其中 1406 条是“低 T 依赖高 T”的反向边（1133 条为真实 value 导入）。根因：wave 只是按 area 轮转，而 `lib/`/`hooks/`/`stores/` 这类大 area 的任务被摊到所有波次里——关键基础（如 `hooks/useI18n.ts`=T341，被 215 个任务导入；`types/index.ts`=T213，被 245 个导入；`stores/settingsStore.ts`=T458；`lib/databaseTypes.ts`=T450）落到了很靠后的 T，而大量早期任务已经依赖它们。另有 1602 条跨 shard 边需要机器间协调。

**建议（最小改动优先）：**

1. **先做 foundation pre-pass**：在开启 wave 之前，先迁 §3.1 表里的高扇入 L0/L1 基础任务。前 10 个任务即可消除 28% 的反向边，前 30 个消除 42%；若接受前移约 100 个任务可消除 65.8%。优先 `T341`(useI18n，若 i18n 基座已复用则可标记 satisfies)、`T213`(types/index)、`T458`(settingsStore)、`T450`(databaseTypes)、`T629`(tableChanges)、`T131`(platform/contracts)、`T431`(schemaStore)、`T354`(panelStore)、`T091`(types/chart)、`T567`(context menus)。
2. **层内再做 wave**：在每个 wave 内按 `L0 → L1 → L2 → L3` 排序挑选（保持“连续任务不同 area”的约束不变），使组件/页面在其依赖之后而不是之前被拿起。
3. **跨 shard 协调**：§4 的边中 seg1→seg2(330)、seg3→seg2(234)、seg1→seg3(224) 最多；建议把“基础 area（lib/hooks/stores/types/commands/platform）”的下游就绪状态作为共享 barrier，或在被依赖方尚未落地时允许上游机器用接口 stub 先行。
4. **环不是阻塞**：10 个 SCC 中最大 53 节点为 type-only 假环；仅 value 的真实环最大 4 节点，按“先接口后实现”即可解开，无需为环调整全局顺序。
