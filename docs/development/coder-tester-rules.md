# datazen 开发流程规则：coder/tester 模式

> **适用对象**：参与本仓库开发的所有 AI agent（coder / tester / 协调者）与人类协作者
> **生效范围**：所有按任务编号（TN）推进的开发工作
> **核心原则：写代码的人不给自己判卷。**

## 0. 角色定义

| 角色 | 职责 | 对源码的权限 |
|------|------|------|
| coder | 实现任务：源码 + 单元测试 + 提交 | 可写 |
| tester | 独立验证：门禁 + 探针 + 测试报告 | **只读** |
| 协调者 | 分派任务、汇总结果、决定放行/返工 | 不直接写业务代码 |

同一个 agent 可以在不同任务里扮演不同角色，但**同一个任务里 coder 与 tester 必须是不同的 agent**（视角必须独立）。

## 1. 三段式交付流程（每个任务走完三段才算完成）

| 段 | 执行者 | 产出 | 提交 |
|----|--------|------|------|
| ① 开发 | coder | 源码 + 自带单元测试 | `feat(<scope>): <描述> (issue-N TN)` |
| ② 验证 | tester | 门禁结果（G）+ 探针结果（P）+ 测试报告 | 报告文件随③提交 |
| ③ 收尾 | 协调者或 tester | tasks.md 关 TN 开 TN+1 | `docs(issue-N): close TN, start TN+1` |

tasks.md 状态只有三值：未开始 / 进行中 / 已完成。**只有走完第③段才允许标「已完成」。**

## 2. coder 守则

1. 动手前必读：任务对应的设计文档章节 + 前序任务的测试报告（了解已知的坑）
2. 交付物 = 源码 + 单元测试，缺一不可；测试必须随源码同一笔提交
3. 自测全过才许提交；测试命令见 §4 门禁，全部从仓库根目录运行
4. 发现任务范围外的 bug：小 bug 可顺带修，但必须 a) 在提交信息中单独说明 b) 在测试报告中申报（参照 T01 的 BUG-001/002 先例）；大 bug 停下报协调者
5. 提交后向协调者申报完成，进入验证队列；**不得自行标记任务完成**
6. 遵守项目红线，如：时间处理禁止 `new Date(string)` 隐式解析无时区文本；不新增未经批准的 npm 依赖

## 3. tester 守则

1. **对源码只读**。发现 bug 不许修，只记录：文件 + 行号 + 复现输入 + 预期/实际
2. **重跑已有测试不算验证**——已有用例过不过是门禁 G1 的事；tester 的核心价值是 §5 的对抗性探针
3. 心态对立：目标是"弄死这段代码"，不是"确认它能跑"。重点打：设计红线、边界条件、PRD 验收锚点、前序提交申报的修复点
4. 门禁任何一项失败 → 拒绝收尾、如实上报，不得美化结论
5. 探针临时文件用完必须删除，最终 `git status --short` 不得有任何探针残留
6. 报告落盘 `docs/development/<issue>/testing/TN-<名称>.md`，格式见 §6

## 4. 门禁清单（G，每任务必跑，仓库根目录）

| 编号 | 命令 | 通过标准 |
|------|------|------|
| G1 | `npx vitest run <本任务路径> --retry=0` | 全过（--retry=0 排除侥幸通过） |
| G2 | `pnpm typecheck` | 退出码 0 |
| G3 | `node scripts/check-test-module-naming.mjs` | 退出码 0 |
| G4 | `pnpm test`（全量回归） | 全过；超 10 分钟可中断并注明 |

新增门禁必须同步更新本表。

## 5. 对抗性探针（P）设计规则

每任务 8–12 个探针，按任务性质覆盖以下类型：

1. **PRD 验收锚点**：PRD 给出的具体输入输出逐个命中
2. **设计红线**：设计文档明令禁止的行为必须被拒绝
3. **边界/歧义输入**：DST 双义与不存在时间、精度极限（微秒/纳秒）、超大数值
4. **非法组合**：配置项互斥组合必须被校验拒绝
5. **稳定性**：同类错误的原因码一致
6. **回归点**：前序提交申报的 bug 修复必须重点复验

每个探针记录五元组：**目的 / 输入 / 预期 / 实际 / 判定**。

## 6. 测试报告模板

```markdown
# TN <任务名> 验证报告
## 范围
（被验证的提交哈希、文件清单）
## 门禁
| 编号 | 命令 | 结果 |
## 探针记录
### P1 <名称>
- 目的 / 输入 / 预期 / 实际 / 判定
## 结论与遗留
（是否放行；发现的 bug：文件+行号+复现输入）
```

## 7. git 与提交规范

1. 一个 issue 一条 feature 分支
2. 提交格式：`feat(scope): ... (issue-N TN)` / `docs(issue-N): close TN, start TN+1`
3. 作者身份保持一致（`git log -1 --format='%an %ae'` 查，用 `git -c user.name=... -c user.email=...`）
4. 每完成一段即 push；push 失败不阻塞开发，记录原因稍后重试
5. 收尾提交前 `git status --short` 必须只含预期文件（tasks.md + 报告），有其他变更先查清

## 8. 并行开发规则（可选模式）

1. **允许**：tester(N) ∥ coder(N+1) 跨任务并行（N 已提交，N+1 消费的是已提交接口）
2. **禁止**：同一任务内 coder∥tester 并行（tester 必须面对已提交的完整代码）
3. 并行 agent **必须用 git worktree 隔离**（`git worktree add ../<repo>-tN`），避免 index.lock 冲突与半成品互相污染
4. 风险条款：N+1 建在未验证的 N 之上，tester 挖出 bug 则 N+1 局部返工
5. 默认顺序执行；并行须协调者显式批准

## 9. 协调者决策规则

1. 收到 tester 报告后三选一：**放行**（收尾提交）/ **返工**（bug 打回 coder）/ **阻塞**（严重问题升级用户）
2. 对照检查：门禁数量与 §4 一致、探针覆盖 §5 类型无缺口，缺了退回补
3. 不亲自写业务代码；跨会话知识沉淀文档（交接文档、本规则）可亲自写
4. 每任务完成后播报进度（一句状态 + 提交哈希）

## 10. 反面清单（一律视为违规）

- coder 自测通过就标任务完成（缺独立验证）
- tester "顺手修个 bug"（只许记录，不许动源码）
- tester 重跑已有测试充数探针（探针必须是新输入）
- 收尾提交里混入源码改动（收尾只动 tasks.md + 报告）
- 门禁失败仍写"基本通过"
- 探针临时文件遗留在工作区
- 无时区文本用 `new Date(string)` 解析（项目红线）
