# Shared feature services

`packages/feature-core` contains the reusable Workflow, AI, MCP, Dashboard/Monitor, metadata/query, export and backup/restore logic. It depends on shared domain crates, runtime, application and platform contracts. F-12 rejects desktop and server transport dependencies.

## Host bindings

- `WorkflowHost` supplies AI completion, command execution and profile migration bindings. Templates, conditions, data steps, timeout/error recovery and result shaping run in the shared executor.
- `ResourceExecutionHost` supplies authorized context, immutable target resolution, profile revision and registry lookup. Shared code issues idempotency tokens, dispatches independent Runtime resources, awaits terminal state, requests cancellation and reads result artifacts. Workflow commands and live AI/MCP database tools use this service.
- `MigrationHost` binds profile repositories, run history and the existing migration plan/job adapters. Profile validation, destructive policy, failure/result mapping and SQL-file token sanitation have a single shared implementation.
- `AiToolLoopHost` supplies tool I/O. The shared tool loop owns streaming round assembly, classification, budgets, cancellation checks and redaction. Shared AI use cases own Chat/NL2SQL request assembly, SQL/EXPLAIN/connection/history analysis, natural-language filter validation and schema documentation selection/formatting. Shared prompt helpers format host-read context files and connection diagnostic metadata; host adapters retain file/profile reads and egress redaction. Shared ownership policy binds granted DB tool targets and annotates structured results; `AiSettingsConfig::selected_profile` centralizes active/default/first selection. These services receive providers, prompt resolvers, schema context and sanitized input from the host; they do not read host profile/history stores or bind Tauri events. `SchemaContextSource` supplies database metadata; the production desktop source reads the explicit session-to-profile mapping, then dispatches metadata against independent Runtime targets. The legacy metadata source remains an explicit compatibility/test adapter.
- `WidgetExecutionHost` binds Workflow execution and run persistence. Result conversion and alert evaluation are shared. `MonitorHost` supplies dashboards, concurrency policy and result delivery; the shared scheduler owns due decisions, in-flight state and per-workflow serialization. Notification transitions/cooldowns are shared; native notification and webhook delivery remain adapters.
- `ExportSource`/`ExportEvents` and `BackupSource`/`BackupEvents` bind authorized sources and event delivery. Formatting, file planning, archive construction, independent backup/restore sessions, SQL decoding and statement guards are shared. Native dialogs and local source lookup remain desktop adapters. Built-in prompts have one canonical source under `packages/feature-core/resources/prompts`; desktop bundling points to that directory. These services accept host-provided paths; a server must bind its artifact/storage root rather than accept an arbitrary client path.

`packages/workspace-apps` additionally owns the installed-app registry, URI grammar, path/MIME policy and routing decisions. Tauri only converts outcomes into native protocol responses and frontend events.

## Settings

`platform-api::settings` separates `UserPreferences` from authoritative `ExecutionSettings`. `SettingsRepository` is bound by its host to an authorized settings scope; `application::settings::SettingsService` validates and normalizes writes. A future server must authorize execution-policy updates before using that repository binding. No server/auth implementation is implied by these ports.

`BackendClient.getSettings/saveSettings` carry only the shared snapshot. The desktop adapter preserves the existing local file format and routes native settings through its native command boundary. Credentials, stdio launch configuration, local paths, update/tray configuration and onboarding do not enter the shared snapshot. Unknown local settings fields survive rewrites. SQL formatting/snippets/workflow result ordering are now persisted by Rust. Query defaults and editor font defaults agree between frontend and backend; backend result limits cannot be widened by client input. Global strict AI egress can tighten model-profile policy.

## Compatibility boundaries

This migration preserves registered Tauri commands and old Rust import paths as adapters/re-exports. It does not delete the legacy `ConnectionManager` or `execute_driver_command` APIs: existing editor/session bridges, migration plan adapters, local export/backup source lookup and local session-to-profile identity lookup still bind those desktop facilities. Shared feature code imports neither type. Native MCP transport/session startup and filesystem/secret repositories also remain host implementations. A server can implement the declared ports without linking Tauri; it still needs its own auth, persistence, artifact and transport bindings.

The Settings UI omits native-only sections when a remote backend is selected. The portable preferences/execution policy remain available through the backend client. AI credential/profile management, stdio MCP setup and native extension/tunnel settings remain desktop-host UI until equivalent server APIs are provided.

## Final residual audit (2026-10-17)

The audit follows development-plan §10 and consumer-adapters §8. Shared-code extraction and P6 resource-model acceptance are separate milestones. This change does not close the latter.

Additional shared rules extracted during the audit:

- `services::command_policy`: command discovery/metadata override/catalog fallback, connection and interactive-command preflight, permission-level mapping, parameter binding, JSON target injection and row-count shaping. The legacy driver-command adapters delegate these rules; their session resolution, stream registration, history persistence, native dialogs and file writes remain desktop bindings.
- `services::migration_endpoint`: normalized physical endpoint identity, driver defaults, tunnel/option credential exclusion, stable digest and fail-closed admission. Desktop `session_identity` only resolves owner/configuration and delegates identity computation. Pure identity tests moved with the implementation; the session lookup integration test remains in the host.
- `dashboard::create`: widget creation/update policy, hidden Workflow construction, layout/defaults and validation behind `WidgetCreationHost`. The desktop implementation binds AppDb and WorkflowRegistry.
- `dashboard::archive`: archive version/format parsing, webhook stripping and portable serialization. Desktop archive code binds local WorkflowRecord conversion, repository lookup/persistence and collision handling.
- `export::prepare_export`: file/container planning. Workflow migration SQL-file parsing, transfer outcome shaping and rollback-history mapping now also live in feature-core.

Actual retained boundaries:

- `commands/driver_command/{resolve,execute,streaming}` still serves existing desktop editor/session IPC and explicitly invokes legacy driver/session APIs. It is not the AI/MCP/Workflow default gateway; those use `ResourceExecutionHost`. Deleting this API before replacing editor/session consumers would break compatibility.
- `services/{db_tools,query_executor,schema_scope,schema_metadata}` are shared re-exports, thin host argument/error bindings, or host integration tests. `feature_ports` contains the explicit ConnectionManager compatibility implementation and the live AppState Runtime implementation.
- `ai/metadata_source` resolves the native logical-session-to-profile identity, then reads metadata through independent Runtime targets. Its required get_session method rejects physical-handle exposure. The schema pipeline, caching/budget selection and output shaping are shared.
- `monitor/connections` is a retained native tunnel/pool compatibility registry. Static call-site audit finds its get/connect/disconnect operations used only by its tests; the active MonitorEngine delegates to the shared scheduler and executes widgets through Workflow. Construction/AppState copies are compatibility plumbing, not evidence that monitor queries still use this pool.
- `workflow/migration` binds profile repositories/history, dedicated native session setup/teardown and the already-existing P5 plan/job adapters. It does not introduce another migration engine. Profile policy and outcome rules are shared.
- Native export binds a logical desktop source session and event delivery; the shared exporter still calls driver `query_stream_at`. Backup/restore binds configuration/driver identity and events; shared backup/restore opens independent driver connections. The original direct-path helpers remain compatibility/test APIs; current table export and backup native entry points use Job/Artifact delivery, and restore now uses a fail-closed apply Job (see follow-ups below).
- Local dashboard/run/history repositories, stdio/native MCP startup, tunnel/secret providers, tray/menu/updater, OS notifications/dialogs and file destinations remain host implementations.

Still outside this extraction's completed evidence: Workflow session/transaction-block semantics and their fault journeys, AI editor-session grants/revocation, MCP owner/TTL cleanup, Wapp stateful ownership, delegated schedule authorization, native-tool process budgets, and real-driver restore Gateway execution. Table export and database backup now use the desktop Job/Artifact delivery path; backup execution still uses the existing desktop driver adapter. The server/auth host is not implemented. These are the remaining P6 stage acceptance items; existing host unit tests must not be presented as their verification.

Verification handoff: the preceding implementation snapshot passed 1,360 Host tests (6 ignored). The residual extraction above has only been rustfmt'ed and statically inspected; it requires a new isolated tester run.

## File Job follow-up (implementation pending isolated verification)

Table export now admits a durable `tableExport` Job through the existing `DesktopJobHost`. Its stage receives a cooperative cancel token, reads each table through independent Runtime targets, renders into host-owned temporary storage, and publishes 64 KiB chunks to ArtifactStore. Artifact references are persisted by JobRuntime before native delivery. Failure/cancellation aborts a writer; success finalizes it. A truncated source query is rejected rather than presented as a complete file. The dialog destination is never part of the Job payload; delivery uses `DesktopDialogHandle`. The durable payload stores only plan versions and a bounded file extension. `get_file_job`/`cancel_file_job` expose status and cancel intent; `export_file_job` retries delivery of the existing artifact without re-executing a query. The existing `Saved(rows)` result remains compatible. Native delivery uses exclusive creation, so a pre-existing destination is rejected; the complete artifact remains available for another destination.

The shared `file_job::FileArtifactJob` owns artifact publication/abort and refuses automatic recovery replay. `FileJobOperation` supplies only a host-owned staging path, not a deserialized client destination. Regressions cover raw-byte publication, principal ACL, pre-dispatch cancellation, failed producer output, and Runtime export leaving the editor session alive. They have been added but not run by the coder.

Backup remains a distinct unfinished gateway migration: ResourceProvider has no dump/native-tool operation, and its backup domain remains undeclared. SQL restore now uses the existing retained-resource execute contract through RuntimeConnectionUseCases and ExecutionGateway, with explicit PostgreSQL/MySQL `retainedSqlRestoreV1` opt-in. This SQL format is narrower than full native backup/restore: COPY and client directives are rejected before writes, and native-tool restore remains future work. No legacy ConnectionHandle wrapper is used by the production restore path.

Workflow session/transaction blocks similarly require new versioned YAML variants plus Runtime block/lease/transaction orchestration, not merely moving the old executor. Owner/TTL requires adapter-supplied MCP/Wapp instance identity and cleanup/revocation hooks; delegated scheduler authorization needs a persisted service/delegation identity checked before dispatch. Current schedules persist cron targets only and `WorkflowScheduleHost::execute_workflow(id)` carries no delegated context. These interfaces cannot be represented honestly by manufacturing a local principal in shared code; the narrow next change is explicit owner/context ports and fail-closed checks before resource acquisition, followed by the defined fault journeys.

## Restore Apply Job follow-up

The native restore entry now uploads an owner-scoped Artifact and submits `databaseRestoreApply` through JobRuntime; it no longer executes a selected path in production. Shared RestorePlan freezes the explicit target/revision/input digest, and the durable repository consumes its plan exactly once. RestoreGateway separates authorization/capability validation from effect-bearing execution and preserves Unknown evidence. PostgreSQL and MySQL explicitly opt into DesktopRestoreGateway, which preflights the complete script, opens a counted fixed Runtime session, observes its target before writing, and persists actual execution IDs and commit boundaries. PostgreSQL supports owned single-transaction execution; MySQL rejects that option before writing because DDL implicitly commits. Other drivers inject UnsupportedRestoreGateway and record Failed/NotStarted until P10. Artifact metadata is checked against the full frozen target fingerprint before Gateway execution. Legacy path restore remains compiled only for compatibility tests. Supported SQL restore has a production execution path; offline and explicitly invoked live journeys are present, with execution verification still required in an isolated tester checkout. Bounded format details and retry-safe structured outcomes are documented below. See [Job §2.5](data-migration-jobs.md#25-restore-apply-job已接线驱动执行失败关闭).
