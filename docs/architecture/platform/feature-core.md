# Shared feature services

`packages/feature-core` contains the reusable Workflow, AI, MCP, Dashboard/Monitor, metadata/query, export and backup/restore logic. It depends on shared domain crates, runtime, application and platform contracts. F-12 rejects desktop and server transport dependencies.

## Host bindings

- `WorkflowHost` supplies AI completion, command execution and profile migration bindings. Templates, conditions, data steps, timeout/error recovery and result shaping run in the shared executor. The command chain itself is shared too: `workflow::command_runtime` validates explicit `database`/`schema` input, resolves connection inheritance and dispatches the command as a workflow-scoped command, so the desktop file under `src-tauri/src/workflow/command_runtime.rs` only binds that chain to `AppState`. `workflow::migration_outcome` holds the shared result vocabulary of a migration step (data transfer, data sync and schema diff alike); the desktop binding only runs the engine and reports what came back.
- `ResourceExecutionHost` supplies authorized context, immutable target resolution, profile revision and registry lookup. Shared code issues idempotency tokens, dispatches independent Runtime resources, awaits terminal state, requests cancellation and reads result artifacts. Workflow commands and live AI/MCP database tools use this service.
- `MigrationHost` binds profile repositories, run history and the existing migration plan/job adapters. Profile validation, destructive policy, failure/result mapping and SQL-file token sanitation have a single shared implementation.
- `AiToolLoopHost` supplies tool I/O. The shared tool loop owns streaming round assembly, classification, budgets, cancellation checks and redaction. Shared AI use cases own Chat/NL2SQL request assembly, SQL/EXPLAIN/connection/history analysis, natural-language filter validation and schema documentation selection/formatting. Shared prompt helpers format host-read context files and connection diagnostic metadata; host adapters retain file/profile reads and egress redaction. Shared ownership policy binds granted DB tool targets and annotates structured results; `AiSettingsConfig::selected_profile` centralizes active/default/first selection. These services receive providers, prompt resolvers, schema context and sanitized input from the host; they do not read host profile/history stores or bind Tauri events. `LogicalSchemaContextSource` supplies database metadata; its implementation now lives in this crate as `feature_core::services::schema_context` — the shared `RuntimeSchemaContextSource` reads the explicit session-to-profile mapping through `RuntimeConnectionUseCases`, then dispatches metadata against independent Runtime targets. It holds only the Runtime facade and a `ResourceExecutionHost`, so the host injects the execution binding and keeps no metadata adapter of its own; a form whose Runtime is not wired binds `UnavailableSchemaContextSource` and every read reports that reason. The port carries neither a physical handle nor a caller-supplied schema cache: the Runtime path owns no live handle, so `get_session` on the metadata port was a method that could only ever fail there, and the three defaults built on it were unusable by every implementation. The physical half is therefore a separate contract — `PhysicalSchemaContextSource`, for a form that owns live connection handles — and `PhysicalSchemaContextAdapter` bridges it into the logical one, owning the schema cache that memoizes the handle-based reads.
- `dashboard::schedule_grant::validate_read_only_sql` enforces the PostgreSQL/MySQL Monitor grant SQL boundary before scheduling and again through desktop Runtime policy. Relation names must contain one identifier; schema/database/catalog qualification is rejected recursively in joins, subqueries and CTEs, including quoted names. This deliberately refuses even apparently matching namespaces rather than guessing dialect-specific case/quoting equivalence. Single-part quoted relation names, aliases and qualified columns remain supported.
- `WidgetExecutionHost` binds Workflow execution and run persistence. Result conversion and alert evaluation are shared. `MonitorHost` supplies dashboards, concurrency policy and result delivery; the shared scheduler owns due decisions, in-flight state and per-workflow serialization. Notification transitions/cooldowns are shared; native notification and webhook delivery remain adapters.
- `ExportSource`/`ExportEvents` and `BackupSource`/`BackupEvents` bind authorized sources and event delivery. Formatting, file planning, archive construction, independent backup/restore sessions, SQL decoding and statement guards are shared. Native dialogs and local source lookup remain desktop adapters. Built-in prompts have one canonical source under `packages/feature-core/resources/prompts`; desktop bundling points to that directory. These services accept host-provided paths; a server must bind its artifact/storage root rather than accept an arbitrary client path.

The Workspace App kernel — manifest schema and rules, package install, per-wapp key-value storage, the installed-app registry, URI grammar, path/MIME policy and routing decisions — is merged into this crate as the `feature_core::workspace_apps` module, because a Workspace App is a generic feature rather than a separate package. The host keeps only the `datazen://` protocol adapter, which converts outcomes into native protocol responses and frontend events.

## Settings

`platform-api::settings` separates `UserPreferences` from authoritative `ExecutionSettings`. `SettingsRepository` is bound by its host to an authorized settings scope; `application::settings::SettingsService` validates and normalizes writes. A future server must authorize execution-policy updates before using that repository binding. No server/auth implementation is implied by these ports.

`BackendClient.getSettings/saveSettings` carry only the shared snapshot. The desktop adapter preserves the existing local file format and routes native settings through its native command boundary. Credentials, stdio launch configuration, local paths, update/tray configuration and onboarding do not enter the shared snapshot. Unknown local settings fields survive rewrites. SQL formatting/snippets/workflow result ordering are now persisted by Rust. Query defaults and editor font defaults agree between frontend and backend; backend result limits cannot be widened by client input. Global strict AI egress can tighten model-profile policy.

## Compatibility boundaries

The P6 migration preserves registered Tauri commands and keeps `execute_driver_command` as the desktop editor/session IPC boundary, while removing the legacy `ConnectionManager`. Desktop session identity, physical resources, tunnels and idle reclamation are owned through Runtime plus the `DesktopSessionBackend` adapter. Shared feature code imports neither Tauri nor host implementation types. Native MCP transport/session startup and filesystem/secret repositories remain host implementations. A server can implement the declared ports without linking Tauri; it still needs its own auth, persistence, artifact and transport bindings.

The Settings UI omits native-only sections when a remote backend is selected. The portable preferences/execution policy remain available through the backend client. AI credential/profile management, stdio MCP setup and native extension/tunnel settings remain desktop-host UI until equivalent server APIs are provided.

## Final residual audit (2026-10-17)

The audit follows development-plan §10 and consumer-adapters §8. Shared-code extraction and P6 resource-model acceptance are separate milestones. This change does not close the latter.

Additional shared rules extracted during the audit:

- `services::command_policy`: command discovery/metadata override/catalog fallback, connection and interactive-command preflight, permission-level mapping, parameter binding, JSON target injection and row-count shaping. The legacy driver-command adapters delegate these rules; their session resolution, stream registration, history persistence, native dialogs and file writes remain desktop bindings.
- `services::migration_endpoint`: normalized physical endpoint identity, driver defaults, tunnel/option credential exclusion, stable digest and fail-closed admission. Desktop `session_identity` only resolves owner/configuration and delegates identity computation. Pure identity tests moved with the implementation; the session lookup integration test remains in the host.
- `dashboard::create`: widget creation/update policy, hidden Workflow construction, layout/defaults and validation behind `WidgetCreationHost`. The desktop implementation binds AppDb and WorkflowRegistry.
- `dashboard::archive`: archive version/format parsing, webhook stripping and portable serialization. Desktop archive code binds local WorkflowRecord conversion, repository lookup/persistence and collision handling.
- `export::prepare_export`: file/container planning. Workflow migration SQL-file parsing, transfer outcome shaping and rollback-history mapping now also live in feature-core.

Actual retained boundaries:

- `commands/driver_command/{resolve,execute,streaming}` still serves existing desktop editor/session IPC and explicitly invokes legacy driver/session APIs. It is not the AI/MCP/Workflow default gateway; those use `ResourceExecutionHost`. Deleting this API before replacing editor/session consumers would break compatibility.
- `services/{db_tools,query_executor,schema_scope,schema_metadata}` are shared re-exports, thin host argument/error bindings, or host integration tests. `feature_ports` provides Store-backed catalog/config ports and Runtime-backed execution; it has no ConnectionManager compatibility implementation.
- `services/schema_context` is the shared implementation of the `LogicalSchemaContextSource` port: it resolves the logical-session-to-profile identity through the Runtime facade, then reads metadata through independent Runtime targets. The physical-handle contract `PhysicalSchemaContextSource` is answered with the refusal that rejects physical-handle exposure, because the Runtime path owns no live handle. The desktop binds it at startup (`src-tauri/src/services/schema_context_source.rs`) and injects the `ResourceExecutionHost`; no host-side AI metadata adapter remains. The schema pipeline, caching/budget selection and output shaping are shared.
- MonitorEngine delegates to the shared scheduler and executes widgets through Workflow/Runtime. The unused native `monitor/connections` compatibility registry, its ConnectionManager dependency and AppState/bootstrap copies have been removed. Manual widget execution and the scheduled grant/occurrence lane retain their existing implementations.
- `workflow/migration` binds profile repositories/history, dedicated native session setup/teardown and the already-existing P5 plan/job adapters. It does not introduce another migration engine. Profile policy and outcome rules are shared.
- Table export binds native dialogs, Job/Artifact delivery and progress events; row reads use `RuntimeCommandSource` independent targets. Backup resolves the profile from the Runtime session directory and opens a dedicated `databaseBackup` Runtime session; PostgreSQL/MySQL `backup_dump` reads metadata and rows on its retained resource. Restore uses a fail-closed apply Job and the PostgreSQL/MySQL Runtime Gateway (see follow-ups below).
- Wapp `command.invoke` is checked again by the host against the installed enabled manifest and `command:invoke` permission, then executes a read-only command through an independent Runtime target. The frontend no longer resolves or passes an editor `dbSessionId`. Per-instance Wapp session ownership and TTL cleanup remain open.
- Local dashboard/run/history repositories, stdio/native MCP startup, tunnel/secret providers, tray/menu/updater, OS notifications/dialogs and file destinations remain host implementations.

Still outside this extraction's completed evidence: real-driver Workflow block and transaction journeys, AI editor-session grants/revocation, Wapp per-instance ownership and TTL cleanup, native-tool process budgets, and real-driver restore and scheduled-query journeys. MCP session ownership/TTL and Monitor schedule grants have implementations, but their production boundaries still need the stage's full fault/live-driver acceptance. Table export and database backup use the desktop Job/Artifact delivery path; backup execution uses the retained Runtime resource for PostgreSQL/MySQL. The server/auth host is not implemented. Existing host unit tests must not be presented as real-driver verification.

Verification handoff: the P6 file-job and Wapp Runtime slices have focused isolated verification; the real-driver Gateway and scheduled-query journeys remain unverified.

## File Job follow-up (implemented)

Table export now admits a durable `tableExport` Job through the existing `JobHost`. Its stage receives a cooperative cancel token, reads each table through independent Runtime targets, renders into host-owned temporary storage, and publishes 64 KiB chunks to ArtifactRepository. Artifact references are persisted by JobRuntime before native delivery. Failure/cancellation aborts a writer; success finalizes it. A truncated source query is rejected rather than presented as a complete file. The dialog destination is never part of the Job payload; delivery uses `DesktopDialogHandle`. The durable payload stores only plan versions and a bounded file extension. `get_file_job`/`cancel_file_job` expose status and cancel intent; `export_file_job` retries delivery of the existing artifact without re-executing a query. The existing `Saved(rows)` result remains compatible. Native delivery uses exclusive creation, so a pre-existing destination is rejected; the complete artifact remains available for another destination.

The shared `file_job::FileArtifactJob` owns artifact publication/abort and refuses automatic recovery replay. `FileJobOperation` supplies only a host-owned staging path, not a deserialized client destination. Regressions cover raw-byte publication, principal ACL, pre-dispatch cancellation, failed producer output, and Runtime export leaving its session alive.

Database SQL backup now uses `backup_gateway::backup_to_path`, RuntimeConnectionUseCases and PostgreSQL/MySQL ResourceProvider `backup_dump` with explicit `retainedSqlBackupV1` opt-in. Metadata, DDL and row reads use one retained physical connection. Column names come from retained catalog rows for both empty and populated tables, rather than metadata inferred from a zero-row query. MySQL catalog text accepts UTF-8 binary wire values. PostgreSQL owned-sequence state is read from each quoted sequence relation on the same connection. Row stream `statementColumns` and complete `statementMetadata` are consumed locally within a byte budget; they never enter the SQL dump, and truncated or unknown output fails closed. A host-only binding validates execution ownership/target and admits at most 64 KiB UTF-8 chunks; each producer write awaits the synchronous staging/gzip writer, so no database-wide String or intermediate Runtime Artifact accumulates. INSERT rendering preserves the existing row/byte batch limits and rejects an oversized row. The completed staging file is still published/delivered by FileArtifactJob. Cancellation, stream failure, finalization failure and unconfirmed resource release reject the backup and remove staging. PostgreSQL single-transaction backup uses a read-only repeatable-read transaction; MySQL uses a consistent snapshot (nontransactional tables retain engine limitations). Other drivers and native-tool backup remain unsupported in this path. Offline renderer tests and opt-in driver-local live journeys cover bounded rendering, gzip, cancellation and oversized-row cleanup; native picker/delivery and complete restore round trips require independent acceptance. SQL restore now uses the existing retained-resource execute contract through RuntimeConnectionUseCases and ExecutionGateway, with explicit PostgreSQL/MySQL `retainedSqlRestoreV1` opt-in. This SQL format is narrower than full native backup/restore: COPY and client directives are rejected before writes, and native-tool restore remains future work. No legacy ConnectionHandle wrapper is used by the production restore path.

Workflow retains its existing v1 protocol, cross-database steps and step-output/template chaining. Only underlying connection management uses `feature-core command_runtime → feature-core resource_execution → Runtime`. P6 does not add session/transaction blocks, dedicated Workflow Jobs or PG/MySQL transaction proof. Existing model/YAML/IPC contracts remain unchanged. Scheduler runtime entry, Monitor, Wapp, MCP and other Job consumers remain separate retained implementations; real-driver v1 acceptance is still required.

## Restore Apply Job follow-up

The native restore entry now uploads an owner-scoped Artifact and submits `databaseRestoreApply` through JobRuntime; it no longer executes a selected path in production. Shared RestorePlan freezes the explicit target/revision/input digest, and the durable repository consumes its plan exactly once. RestoreGateway separates authorization/capability validation from effect-bearing execution and preserves Unknown evidence. PostgreSQL and MySQL explicitly opt into DesktopRestoreGateway, which preflights the complete script, opens a counted fixed Runtime session, observes its target before writing, and persists actual execution IDs and commit boundaries. PostgreSQL supports owned single-transaction execution; MySQL rejects that option before writing because DDL implicitly commits. Other drivers inject UnsupportedRestoreGateway and record Failed/NotStarted until P10. Artifact metadata is checked against the full frozen target fingerprint before Gateway execution. Legacy path restore remains compiled only for compatibility tests. Supported SQL restore has a production execution path; offline and explicitly invoked live journeys are present, with execution verification still required in an isolated tester checkout. Bounded format details and retry-safe structured outcomes are documented below. See [Job §2.5](data-migration-jobs.md#25-restore-apply-job已接线驱动执行失败关闭).
