# 设计：类 Chrome 浏览器插件可行性分析

**日期：** 2026-08-09  
**分支：** `docs/chrome-like-extensions-feasibility`  
**工作区：** `.worktrees/chrome-like-extensions`  
**状态：** 可行性草案（方向未定；覆盖方案 A/B/C）  
**范围：** 架构可行性与产品取舍，不含实现计划

## 目标

1. 评估在 DataZen（Tauri v2 + React）中引入「类似 Chrome 浏览器插件」能力的可行性。
2. 用两个代表性场景锚定价值：**数据对比校验**、**自定义经营数据面板**。
3. 给出三种可落地路径（A 开放运行时扩展 / B 可信功能包 / C 一等公民功能）的完整对比，便于后续选型。
4. 明确与现有体系的关系：编译期驱动插件、运行时主题包、Workflow、MCP、数据同步。

## 非目标

- 本文件不选定最终产品方向（见用户选择 D：先完整对比）。
- 不写实现计划、不改代码、不引入新依赖。
- 不设计 Chrome Web Store 级分发与审核运营细节（仅标出缺口）。
- 不重新设计驱动选型（`drivers-registry.json` / `resolve-drivers.mjs`）或主题包格式。

## Chrome 扩展心智模型（对照基准）

| Chrome 概念 | 典型能力 | DataZen 现状 |
|-------------|---------|--------------|
| 清单文件 + 权限 | 声明可访问的 API / 主机 | 无用户级扩展权限模型；Tauri capabilities 按构建注入 |
| 内容脚本 | 注入页面 DOM | 无；单一前端应用，CSP 为 `script-src 'self'` |
| 弹窗 / 侧边栏 | 轻量扩展界面 | 固定窗口类型 + 硬编码操作面板 |
| 后台 / Service Worker | 常驻逻辑 | Rust 后端 + Zustand；无用户 JS 后台 |
| 消息 API | `chrome.runtime.sendMessage` | 固定 `invoke()` IPC 接口面 |
| 运行时安装 / 更新 | 商店或旁加载 | 仅主题 ZIP（无 JS）；驱动需重编译 |
| 隔离执行 | 扩展进程 / 隔离世界 | 全窗口同源、同一 webview 应用 |

结论：**「类 Chrome」不是界面隐喻问题，而是「不可信代码 + 权限 + 隔离 + 分发」平台问题。**

## 现状（现有扩展层）

### 1. 编译期驱动插件（主插件体系）

- **模型：** Caddy 式构建选型；Rust crate + 可选 React 界面打进二进制。
- **入口：** `drivers-registry.json`、`scripts/resolve-drivers.mjs`、`packages/driver-api`、`src/plugin-sdk`。
- **已落地插槽：** 连接表单、自定义 Schema 树、方言、驱动图标、可选 Tauri 插件命令。
- **RFC 未落地插槽：** `main-panel`、`toolbar-actions`、`settings-panel`、`sidebar-section`（见 `docs/rfc-plugin-system.md`）。
- **显式非目标：** 运行时动态插件（`docs/superpowers/specs/2026-08-07-plugin-command-acl-design.md`）。

### 2. 运行时主题包（仅外观）

- **路径：** `{appData}/themes/{id}/`（本地 ZIP）。
- **允许：** CSS / JSON / 图像 / 字体。
- **禁止：** JS / WASM；与驱动选型完全独立。
- **先例：** 运行时安装通道已存在，但刻意不含代码执行。

### 3. Workflow + MCP（自动化，非界面扩展）

- **Workflow：** YAML 步骤（query / ai / condition / foreach）；无可任意脚本/HTTP 步骤。
- **MCP 服务端/客户端：** 对外工具面与 AI 工具调用；权限分档（只读 / 安全写 / 高危写）。
- **价值：** 适合无头校验流水线与外部集成，不替代应用内面板插件。

### 4. 场景相关宿主能力

| 场景 | 已有能力 | 缺口 |
|------|---------|------|
| 数据对比校验 | 数据同步窗口 + `compare_databases` / `compare_table_schemas` / `compare_table_data` + `sync/` 中间表示 | 规则可插拔性弱；无第三方校验器注册；跨业务校验模板生态缺失 |
| 经营数据面板 | 图表视图 + 查询页签 + Workflow 输出图表；多窗口路由 | 无仪表盘定义格式；无固定刷新/布局槽；主窗口操作面板不可扩展 |

### 5. 安全边界（硬约束）

- CSP：`script-src 'self'`（禁止内联/外部脚本）。
- 文件 IPC：对话框介导；禁止任意路径直读。
- 密钥：AES-256-GCM；不得暴露给扩展 JS。
- 单应用同源：无「每扩展独立 webview / capability 文件」。
- 主题与 ACL 文档均将「运行时动态插件」排除或延后。

## 三种路径

### 方案 A — 开放运行时扩展（最接近 Chrome）

**一句话：** 用户安装第三方扩展包；扩展带清单、权限、隔离界面/逻辑；可注册面板、校验规则、后台任务。

**最小平台组件：**

1. **扩展包格式**（ZIP）：`manifest.json` + 静态资源 + 可选 JS/WASM 入口。
2. **安装通道：** `{appData}/extensions/{id}/`（可复用主题 ZIP 校验管线的形状，但策略相反：允许代码）。
3. **权限模型：** 如 `connections.read`、`query.execute`、`ui.panel`、`net.fetch`、`fs.dialog`。
4. **隔离执行（必选其一或组合）：**
   - **A1 每扩展独立 Webview：** 每扩展独立 Tauri webview + 独立 capability；通过宿主桥发消息。
   - **A2 iframe 沙箱 + 严格 postMessage：** 同窗口嵌入；攻击面小于裸 eval，仍共享进程。
   - **A3 WASM 访客：** 逻辑在 WASM；界面仍由宿主组件或受限 DOM。
5. **宿主 API：** 类似 `chrome.*` 的窄面：`datazen.connections.list`、`datazen.query.run`、`datazen.ui.openPanel`、`datazen.storage.get/set`。
6. **界面插槽：** 落地 RFC 中的 `main-panel` / `sidebar-section` / 主窗口操作面板入口。
7. **分发（可分期）：** 本地旁加载 → 签名 → 商店/CDN。

**对目标场景：**

| 场景 | 如何满足 |
|------|---------|
| 数据对比校验 | 扩展注册校验器；调用查询/对比 IPC；在面板展示差异 |
| 经营面板 | 扩展提供仪表盘布局 + 定时查询 + 图表视图数据契约 |

**优点：** 生态上限最高；第三方可独立迭代；最符合「浏览器插件」叙事。  
**缺点：** 与当前安全默认值冲突最大；工程量与长期维护成本最高；需重做 CSP/capabilities/审计。  
**粗估量级：** 平台骨架 2–4 人月；可信任商店/签名再 +1–2 人月；生态文档与示例持续投入。  
**风险：** 任意代码执行 → 凭据窃取 / 静默写库 / 外传数据；回归与端到端测试复杂度显著上升。

**可行性判定：** **技术上可行，产品上高风险。** 不建议作为第一版；若做，必须先选隔离方案（推荐 A1 或 A3）并禁止默认高危权限。

---

### 方案 B — 可信功能包（受限运行时，无开放商店）

**一句话：** 类似「签名的企业/官方附加包」：可含声明式配置 + 受限界面/逻辑，安装前需信任链（官方签名或企业内部分发），不做任意第三方商店。

**包内容分层（建议）：**

| 层 | 内容 | 信任要求 |
|----|------|---------|
| L0 声明式 | YAML/JSON：仪表盘布局、校验规则、Workflow 模板、查询定义 | 低（类主题包） |
| L1 宿主组件绑定 | 引用宿主已有组件 ID / 插槽，无自定义 JS | 低 |
| L2 受限脚本 | QuickJS / WASM 沙箱，无裸 DOM；仅宿主 API | 中（需签名） |
| L3 完整 React 包 | 动态 `import()` 进主应用 | 高（接近 A，不推荐作为 B 的默认） |

**推荐 B 的默认形态：L0 + L1，可选 L2。**

**复用点：**

- 安装/校验管线：对齐主题包 ZIP 校验（扩展允许列表、路径遍历、大小限制）。
- 界面：落地少量稳定插槽（主窗口操作入口、连接窗口面板、独立窗口类型）。
- 数据：只走现有 IPC（查询 / 同步对比 / Schema）；不开放新的任意 SQL 绕过。
- 自动化：功能包可附带 Workflow 模板。

**对目标场景：**

| 场景 | 如何满足 |
|------|---------|
| 数据对比校验 | 包内校验规则 DSL + 调用现有对比 IPC；结果面板由宿主渲染 |
| 经营面板 | 包内仪表盘 JSON（组件：指标/表格/图表）+ 绑定连接配置 ID / SQL |

**优点：** 覆盖「可安装扩展」叙事约七成价值，安全面可控；与主题包运营模型一致。  
**缺点：** 自定义界面上限低于 Chrome；DSL 设计成本；第三方自由度有限。  
**粗估量级：** L0+L1 约 1–2 人月；加 L2 沙箱再 +1–2 人月。  
**风险：** DSL 若过早复杂会变成「半个编程语言」；需严格版本化宿主 API。

**可行性判定：** **高可行性，性价比最佳的「类插件」路径。** 与现有「运行时 = 数据/声明，编译期 = 代码」哲学兼容。

---

### 方案 C — 一等公民功能（不引入扩展平台）

**一句话：** 不做通用插件运行时；把「数据对比校验」和「经营数据面板」直接做成产品功能，必要时用编译期驱动插件补垂直场景。

**数据对比校验：**

1. 增强数据同步窗口 / `sync/`：规则预设、行级校验报告、导出、定时/Workflow 触发。
2. 提供官方 Workflow 模板（对比 → 条件 → AI 摘要 / 通知）。
3. MCP 暴露对比工具供 CI/外部编排。

**经营数据面板：**

1. 新增窗口类型 `dashboard`（或扩展 Workflow 面板）。
2. 宿主仪表盘定义（JSON）：数据源 = 已保存连接 + SQL/命名查询；组件 = 复用图表视图 / 数据表。
3. 主窗口操作面板增加入口；布局与刷新策略由产品定义。
4. 深定制界面仍走编译期驱动插件（落地 RFC `main-panel`）。

**优点：** 最快交付用户价值；安全模型不变；测试路径清晰。  
**缺点：** 无第三方扩展生态；每个新垂直场景仍可能回到改宿主代码。  
**粗估量级：** 对比增强 0.5–1.5 人月；仪表盘最小可用版本 1–2 人月（视刷新/布局复杂度）。  
**风险：** 若用户真实需求是「装别人写的插件」，C 无法满足叙事预期。

**可行性判定：** **最高可行性 / 最低风险。** 若核心痛点是两个业务场景而非生态平台，应优先 C。

## 对比矩阵

| 维度 | A 开放运行时 | B 可信功能包 | C 一等公民功能 |
|------|-------------|-------------|----------------|
| 用户价值兑现速度 | 慢（先平台） | 中 | 快 |
| 第三方生态 | 高 | 中（受控） | 低 |
| 安全/合规风险 | 高 | 中低 | 低 |
| 与 CSP/主题哲学一致性 | 冲突 | 可对齐 | 一致 |
| 与驱动编译期插件关系 | 平行新平台 | 平行（声明式） | 互补（深定制仍用驱动） |
| 对对比校验场景 | 强（可插拔规则） | 强（DSL） | 强（直接做产品） |
| 对经营面板场景 | 强（任意界面） | 中强（组件 DSL） | 强（宿主仪表盘） |
| 维护成本 | 高 | 中 | 中低 |
| 建议阶段 | 远期 / 需强生态诉求 | 中期平台化 | **近期末选方向时的默认** |

## 建议（在未拍板前提下的工程建议）

> 用户选择了「先完整对比、暂不定方向」。以下为**条件化建议**，不是已批准决策。

1. **若 90 天内要以对比校验 / 经营面板交付价值 → 选 C**，同时把仪表盘 / 校验规则做成**可序列化定义**（为日后 B 留迁移路径）。
2. **若目标是企业内「可安装业务包」且不要开放商店 → 选 B（L0+L1）**，安装通道对齐主题包；脚本执行默认不做。
3. **仅当明确需要不可信第三方扩展市场时再开 A**；且必须以 webview/WASM 隔离 + 权限最小化 + 签名为前提，禁止「主应用动态执行扩展 JS」。
4. **无论选哪条，不要把主题包改成可执行 JS**；外观与行为扩展应保持通道分离（已有架构原则）。
5. **编译期驱动插件继续负责「新数据库 / 深度定制连接体验」**；不要用 A/B 替代驱动 API。

**推荐默认演进路径（供讨论）：** `C（可序列化定义）→ B（安装可信包）→ （可选）A`。

## 目标场景 — 能力拆解（与路径无关）

### 数据对比校验

**用户故事：** 对比两库/两表结构或抽样数据；输出差异报告；可按规则（空值率、主键冲突、金额合计）告警。

**宿主能力清单（任意路径都需要）：**

- 连接选择与权限（只读优先）。
- Schema/数据对比 API（已有基础）。
- 规则定义与结果模型（**缺口**）。
- 报告界面 / 导出（**缺口**）。
- 可选：Workflow/MCP 触发。

**路径差异：** C 把规则写进产品；B 用包分发规则；A 用扩展代码实现任意规则。

### 自定义经营数据面板

**用户故事：** 固定看若干指标/趋势/明细表；绑定生产只读连接；可刷新与多面板布局。

**宿主能力清单：**

- 仪表盘文档模型（组件、布局、查询引用）（**缺口**）。
- 查询执行 + 结果到图表的契约（图表视图可复用）。
- 窗口/导航入口（**缺口**：操作面板插槽或新窗口类型）。
- 刷新策略与错误态。

**路径差异：** C 内置编辑器；B 分发仪表盘 JSON；A 扩展自绘界面。

## 架构示意

### 共享宿主契约（建议无论 A/B/C 都先稳定）

```
DashboardDefinition { id, title, widgets[] }
Widget { type: kpi|table|chart, queryRef, visual }
QueryRef { connectionConfigId, sql | namedQueryId }
ValidationRuleSet { id, target, rules[] }
ValidationReport { diffs[], metrics[], severity }
```

这些契约若先以文件/设置形式存在于 C，日后迁到 B 的 ZIP 几乎零损失。

### 方案 B 安装布局（示意）

```
{appData}/
  themes/{id}/          # 现有：无 JS
  extensions/{id}/      # 新建：功能包
    manifest.json       # id, version, permissions, slots
    dashboards/*.json
    validations/*.json
    workflows/*.yaml    # 可选模板
    # 默认无 .js；若启用 L2 则 wasm/ 或 scripts/ 且需签名
```

### 方案 A 隔离（示意）

```
宿主前端应用
  └─ 扩展桥接（权限检查）
        ├─ webview: ext-data-diff
        └─ webview: ext-ops-dashboard
Rust：按扩展标签划分 capability 文件
IPC：仅将白名单宿主命令代理到桥接层
```

## 安全要求（若涉及运行时代码）

1. **默认拒绝**高危权限：任意 SQL 写、原始文件系统、读取 AI/连接密钥。
2. **查询默认只读连接**，或强制与 MCP 权限模式等价的门闸。
3. **无 `eval` / 无主世界内容脚本**；扩展不得修改宿主 DOM。
4. **签名或企业信任锚**（B-L2 / A 必选）。
5. **资源配额：** 结果行数、CPU/定时器、网络域名白名单。
6. **审计日志：** 扩展发起的查询/对比/网络请求可追溯。
7. **卸载干净：** 删除 `{appData}/extensions/{id}` 及其本地存储，不影响主题包与驱动。

## 开放问题（选型前需拍板）

1. 目标用户是「终端业务用户装包」还是「我们自己交付垂直功能」？
2. 是否必须支持不可信第三方？（是 → A；否 → B 或 C）
3. 经营面板是否需要完全自定义 React 界面，还是组件 DSL 足够？
4. 对比校验是否要跨非 SQL 源（API/Excel），还是库表即可？
5. 分发是否需要商店/CDN，还是本地 ZIP / 企业内部路径足够？

## 决策速查表

| 若你同意… | 则倾向… |
|-----------|--------|
| 先交付场景，生态以后再说 | C，定义可序列化 |
| 要「安装包」体验，但只要官方/企业包 | B（L0+L1） |
| 要开放市场与任意扩展代码 | A（隔离+签名），并接受长周期 |
| 只要换肤 | 已有主题包，停止扩展讨论 |
