## Bug 描述

### 场景
在 SQL 查询编辑器中使用 NL2SQL 功能生成 SQL 后，点击"应用到编辑器"按钮，编辑器中被写入的是 AI 模型的完整推理过程（包括中文解释、逻辑分析等），而非仅生成的 SQL 语句。

### 预期结果
点击"应用到编辑器"后，编辑器中应仅包含生成的 SQL 语句，例如：
```sql
SELECT t.* FROM test_logistics t;
```

### 实际结果
编辑器中被写入了约 13 行内容，包含 AI 的完整推理过程：
```
...用别名，所以我们写 SELECT t.* FROM test_logistics AS t; 或者直接 SELECT * FROM test_logistics t; 我认为最好列出
所有列? 但规则没要求。我们只需返回可执行 SQL。

注意：数据库是 MySQL。所以正确。

最终 SQL: SELECT * FROM test_logistics; 但加别名: SELECT t.* FROM test_logistics t;

我决定写: SELECT t.* FROM test_logistics t;

这符合要求。SELECT t.* FROM test_logistics t;
```

## 重现步骤

1. 启动 DataZen 应用并打开 MySQL 连接窗口
2. 点击"新建查询"创建查询标签页
3. 点击工具栏中的"AI 生成 SQL"按钮
4. 在自然语言输入框中输入："select all from test_logistics"
5. 按 Enter 或点击"生成 SQL"按钮
6. 等待 AI 生成完成（约 10 秒）
7. 点击底部的"应用到编辑器"按钮
8. **实际结果**：编辑器中包含完整推理文本
9. **预期结果**：编辑器中仅包含 SQL 语句

## 根因分析（推测）

可能的原因：
1. DeepSeek 模型的 OpenAI Responses 协议返回中包含了 reasoning/thinking tokens，应用没有正确过滤
2. AI 模块的 `ai_generate_sql` 函数在提取 SQL 时，没有从流式响应中正确提取代码块中的 SQL
3. Prompt 模板可能需要更明确地指示模型只返回 SQL（无推理过程）

需检查：
- `src-tauri/src/ai/prompt.rs` 中 NL2SQL 的 prompt 模板
- `src-tauri/src/commands/ai.rs` 中 `ai_generate_sql` 的响应处理逻辑
- `src/components/ai/Nl2SqlPanel.tsx` 中"应用到编辑器"的实现

---

## 影响范围

- **影响**：使用 NL2SQL 功能的用户无法直接获得可执行的 SQL，需手动清理推理文本
- **关联测试用例**：TC-AI-001, TC-AI-002

---

## 修复说明

**修复提交**：`fix: strip reasoning text from NL2SQL streaming output`

**修复方案**：
1. **后端**：`StreamChunk` 新增 `reasoning` 字段，各 provider 将 `reasoning_content` 单独传递，不再混入 `content`
2. **前端**：新增 `extractSqlFromResponse()` 工具函数，在流式传输完成时对累积内容进行清洗，优先提取 SQL 代码块、过滤推理文本
3. **测试**：新增 11 个单元测试覆盖各种 SQL 提取场景

**修改文件**：
- `packages/ai-api/src/types.rs` — StreamChunk 新增 reasoning 字段
- `src-tauri/src/ai/{openai,anthropic,custom}.rs` — 分离 reasoning 和 content
- `src-tauri/src/commands/ai.rs` — 统一 emit 逻辑
- `src/lib/extractSql.ts` — SQL 提取工具函数
- `src/stores/aiStore.ts` — 流式处理中分离 reasoning，完成时调用 extractSqlFromResponse
